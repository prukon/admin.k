1) Назначение и доступ

После создания договора в режиме «форма клиенту» (creation_mode=template) ученик (родитель в семейном кабинете) видит задачу «Требуется заполнение», открывает модалку, заполняет поля из схемы шаблона, формирует PDF и подписывает договор по SMS (Подпислон). Без API-ключа юрлица подпись не уходит: redirect на fill с errors.podpislon_api_key, статус не failed (анонс). HTTP 200 Подпислона с JSON status: false — отказ: договор failed, SMS не уходит. Текст ошибки в CRM (карточка / журнал / title списка) — анонс, contracts §3.1.2. Карточка «Мои документы» #contract-status-error не рисует. account.documents.sign при отказе — 302 на fill с errors.sign = текст сервиса (не JSON 422 CRM POST /client-contracts/{id}/send).

Когда Подпислон подтверждает подпись (вебхук или ручная синхронизация статуса), договор становится signed и админы школы получают уведомление в колокольчик на 7 суток (анонс, in-app-notifications §5.2). Исключение: если школа уже аннулировала договор (revoked), поздняя подпись старого SMS статус в signed не поднимает и колокольчик не шлёт (анонс аннулирования).

Право на раздел: account.documents.view (Gate::define('account.documents.view')).
Список и каунтер — договоры активного ребёнка (FamilyStudentContextService::activeStudent()), не учётки входа. Маршруты fill / generate / sign / resend-sms защищены middleware contract.owner: договор доступен владельцу (contracts.user_id === Auth::id()) или sibling из accessibleStudents; чужой пользователь получает 404 (anti-enumeration).
Ссылка в письме-приглашении: /account-settings/documents?student={user_id}&fill={contract_id} переключает контекст на ребёнка договора (только свой sibling) и открывает модалку. Без student (меню, PDF) ребёнок не переключается. (анонс).
Гость → 302 на login; без права → 403.

1.0) Каунтер «активных к действию» договоров

На пункте левого меню «Учетная запись» и на вкладке «Мои документы» показывается badge с числом договоров активного ребёнка (contracts.user_id = FamilyStudentContextService::activeStudent()), у которых статус из набора «активных к действию»:

  • awaiting_client_fill — ожидает заполнения клиентом
  • sent — отправлено на подпись
  • opened — открыто подписантом
  • generating_pdf — формируется PDF после заполнения

Не входят в каунтер: draft, signed («Подписано»), expired, revoked, failed. Это не «все кроме signed» — черновики и отозванные/просроченные/ошибочные договоры каунтер не раздувают.

1.2) Семейный кабинет и ссылка из письма

При 2+ детях с одним parent_id список «Мои документы» и каунтер показывают договоры activeStudent() (как консоль и платежи), не учётки входа. Fill / generate / sign / download / requests доступны, если contracts.user_id — сам Auth::id() или sibling из accessibleStudents (FamilyStudentContextService::canAccessContract). Права остаются у учётки входа.

Письмо-приглашение подставляет {{documents_url}} как /account-settings/documents?student={user_id}&fill={contract_id} (ContractInvitationEmailRenderer::documentsUrl). Query student вызывает setActiveStudent только если ученик из accessibleStudents (активный sibling; отключённый брат/сестра в список не входит). Чужой и отключённый id молча игнорируются (не 403) — в отличие от POST /cabinet/active-student, где недоступный ученик даёт 403. Query fill без student ребёнка не переключает (меню, закладка, PDF). В PDF ключ documents_url без query. Гость по ссылке → 302 на login, в url.intended остаются оба query. Generate в модалке (AccountContractGenerateRequest::authorize) тоже через canAccessContract, иначе sibling открыл бы форму, но submit получил бы 403. Анонс: /doc#account-documents-family-link-index.

1.3) Ссылка на подпись из SMS

Анонс: /doc. На карточке /account-settings/documents при Contract::canClientOpenSigningUrl() — подпись «Ссылка на подпись», кнопка «Открыть ссылку из SMS» и сам URL. Оба <a href>: target="_blank", rel="noopener noreferrer". Значение — contracts.provider_signing_url (та же ссылка, что в SMS Подпислона) после whitelist PodpislonSigningUrl::normalize. Без URL кнопки нет. Чужой хост в БД на экран не попадает. signed и revoked с валидным URL тоже показывают кнопку (аннулирование URL не стирает; старое SMS у Подпислона может остаться живым). Статус expired кнопку прячет даже при сохранённом URL (ссылка Подпислона уже мёртвая) — alert на карточке, §1.4. Повтор SMS на тот же номер — §1.5. Кнопка — обычный <a href> в разметке карточки, fill-AJAX её не пересобирает. Native POST account.documents.sign без X-Requested-With → 302 на account.documents.index и URL в БД; 422 errors.signer_lastname URL не пишет. Sibling видит ссылку только при активном ребёнке-владельце договора. CRM: contracts §3.1.1.

Пока fill_expires_at ещё в будущем, на той же карточке отдельно поле оставшихся дней (§1.6); после просрочки заполнения оно скрыто.

1.5) Повтор SMS из кабинета

Анонс: /doc#account-documents-resend-sms-index. Кнопка «Отправить SMS ещё раз» (CLIENT_RESEND_SMS_BUTTON) при Contract::canClientResendSms(): sent / opened / expired, есть provider_doc_id и телефон последней contract_sign_requests (lastSignerPhone()). У школы CRM-ресенд ещё и при failed; в кабинете failed / revoked / signed кнопки нет. Подсказка: «SMS уйдёт на {маска}», маска — RuPhone::formatMaskedForDisplay / clientResendSmsMaskedPhone() (+7 (XXX) ***-**-NN). Полный номер в разметку не пишем. POST account.documents.resendSms, Form Request AccountContractResendSmsRequest (signer_phone и ФИО — prohibited, 422 по этим ключам). Сервис resendFromLastRequest → пакет Подпислона repeat-send, без новых 70 ₽. Cooldown 30 сек (ContractSmsCooldown) → 422 errors.contract. Форма js-contract-resend-sms-form: AJAX POST, 422 под [data-error-for="contract"] (без этого ключа — message), успех — reload. Native POST — 302 и session success / errors.contract (@error('contract')). Native prohibited — session errors.signer_phone, под кнопкой не печатается. После успеха expired становится sent; opened остаётся opened (JSON status при этом sent). Номер всегда с последней contract_sign_requests. fill-AJAX (loadContractFill) пересобирает только модалку, форму на карточке не трогает. Первая отправка из fill-модалки по-прежнему с выбором телефона. CRM #openResendModal не трогаем.

1.6) Оставшиеся дни до срока подписания

Анонс: /doc#account-documents-fill-remaining-days-index. На карточке «Мои документы» (рядом с «Обновлён») поле CLIENT_FILL_REMAINING_CAPTION — «Срок подписания». Источник — fill_expires_at (те же 30 суток, что школа видит при создании: «Срок для подписания договора N дней», FILL_TTL_DAYS). Это не колонка CRM «Срок подписания» (дата-время по contracts.fillExpiresAt.view и вторая строка короткого остатка, contracts §1.4, анонс, остаток в списке), не подпись «Срок заполнения» на карточке CRM (то же поле, формат d.m.Y H:i, без отдельного права), не TTL SMS Подпислона (§1.4).

Показывать: template-режим, fill_expires_at в будущем, статус не signed (shouldShowClientFillRemainingDays()) — в том числе awaiting_client_fill, generating_pdf, draft, sent, opened, expired, failed, revoked. Скрывать: уже signed, PDF-режим, null срок, fill_expires_at в прошлом. Прошлый fill_expires_at у awaiting_client_fill даёт бейдж/alert §1.4; у sent / opened поле дней просто исчезает, SMS это не блокирует.
Значение clientFillRemainingDaysLabel(): «Осталось N дней» (склонение день/дня/дней) или «Последний день» (CLIENT_FILL_REMAINING_LAST_DAY), если дата срока — сегодня, а время ещё не прошло. Счёт календарный: now()->startOfDay()->diffInDays(fill_expires_at->copy()->startOfDay(), false) в Europe/Moscow. Если дней меньше CLIENT_FILL_REMAINING_DAYS_WARN (6), включая 0, значение с text-danger (shouldHighlightClientFillRemainingDays()). Ровно 6 дней — без красного. Новых маршрутов нет.

  • Ширина: класс contract-fill-modal-dialog (max-width 720px).
  • Контент подгружается AJAX: GET …/fill с заголовком X-Requested-With: XMLHttpRequest.

2.2) Поля ФИО и даты

Составные ключи DOCX (parent_full_name, child_full_name) в форме разбиты на части: parent_lastname, parent_firstname, parent_middlename, child_lastname, child_firstname. Ключ parent_full_name_genitive — одно поле (не разбивается), prefill из parents.full_name_genitive. Ключ child_full_name_genitive — одно поле (не разбивается), prefill из users.full_name_genitive. При генерации PDF полные ФИО собираются в ContractPdfGenerationService / ContractTemplateVariablePresets::composeNameFieldsForPdf.

child_birthday — <input type="date">, валидация date + before:today (AccountContractGenerateRequest). Значения в PDF и filled_data — в формате d.m.Y; в профиле ученика — Y-m-d.

2.2.1) Телефон в PDF

Только generate из шаблона (creation_mode=template). Загруженный PDF (creation_mode=pdf) без плейсхолдеров не форматируем. Телефон SMS после generate (signer_phone) — не ключ DOCX, в PDF не попадает.

В форме маска Inputmask +7 (999) 999-99-99 (js-contract-fill-phone, autoUnmask / removeMaskOnSubmit). Submit отдаёт 10 цифр без +7 (например 9062475508); prefill из CRM — 11 цифр с ведущей 7. При generate ContractTemplateVariablePresets::formatPhoneFieldsForPdf (внутри composeNameFieldsForPdf) приводит ключи с phone / tel / mobile к RuPhone::formatForInput: +7 (906) 247-55-08. Это значение идёт в DOCX/PDF и в filled_data. Критерий тот же, что у поля формы (isFillFormPhoneField): parent_phone, student_phone, spouse_phones и кастомные ключи из шаблона. trusted_person_1_contacts — не телефонное поле, строка как есть. Невалидный номер не переписываем. Уже в маске и номер с ведущей 8 тоже приводятся к +7 (…). Карточка родителя по-прежнему сохраняет канон из цифр (StudentParentSyncService::normalizePhonePart снимает маску). Уже сформированный PDF сам не меняется — нужна повторная генерация.

Форма: первое открытие и повторный GET fill показывают prefill из CRM уже в маске (RuPhone::formatForInput в phone-input); пустой номер остаётся пустым. Режим «Изменить» тоже маскирует даже legacy filled_data из 10 цифр. Оба JS-триггера (.js-open-contract-fill / .js-open-contract-fill-edit) после AJAX GET fill вызывают phone-inputmask:refresh. AJAX generate 422 — errors['fields.parent_phone'] под полем; non-AJAX — 302 и session errors. Анонс: /doc#account-contract-phone-mask-index.

2.3) Порядок полей

Поля сортируются по fill_sort_order из fields_schema версии шаблона (или пресета из ContractTemplateVariablePresets). Рекомендуемая шкала: 10–50 основные данные, 200+ супруг(а), 300+ кастомные поля из DOCX. Редактирование порядка в CRM — только с правом contracts.templates.fillSortOrder.edit (по умолчанию только superadmin).

2.4) Предзаполнение

ContractPrefillResolver подставляет значения из карточки ученика/родителя/группы по prefill_source в схеме. Поле parent_email (подпись «Email»): parentEmailOrStudentFallback() — сначала parents.email; если пусто (пробелы / нет карточки) — users.email ученика. Это только модалка fill, не форма /account-settings/user/edit. Подробно — §2.6. После успешного generate данные синхронизируются обратно:

  • ContractParentProfileSyncService — ФИО, паспорт, адрес, телефон и непустой parent_email в parents
  • ContractStudentProfileSyncService — фамилия, имя, дата рождения, адрес проживания (child_address → users.address) и ФИО в родительном (child_full_name_genitive → users.full_name_genitive, только непустое)

2.5) Реквизиты юрлица и child_address

Ключи legal_entity_* из схемы шаблона не показываются в форме родителя (fill_mode=system). При generate их значения мержатся из юрлица группы договора (contracts.group_id → LegalEntityResolver) через ContractLegalEntityPlaceholderService / ContractTemplateSystemPlaceholders и попадают в filled_data и PDF.

child_address — в панели «Ребёнок», prefill из users.address. Если юрлицо не резолвится, а в схеме есть LE-ключи: AJAX generate → 422 errors.contract; non-AJAX → redirect с той же ошибкой. Подробно — contract-templates §6.1.

2.6) Паспорт, email, ошибки под полями (модалка)

Анонс на главной: /doc § паспорт / email / ошибки. Только модалка #contractFillModal на /account-settings/documents. Форма родителя в /account-settings/user/edit — «Паспорт»; админский _parent_form — «Паспорт родителя». Fallback users.email в поле email родителя — только prefill модалки, не форма профиля.

sent / openedFill JSON → 422 «Договор недоступен для заполнения»; подсказка про SMS на странице при других сценариях. Если в БД есть provider_signing_url — на карточке договора кнопка «Открыть ссылку из SMS» и сам URL (target="_blank", noopener noreferrer; §1.3). Если пакет и номер последней отправки есть — кнопка «Отправить SMS ещё раз» и маска номера (§1.5). Школа может аннулировать договор на карточке CRM («Аннулировать», анонс): статус revoked, 70 ₽ не возвращаются. Кнопка «Изменить» в кабинете не появляется. В каунтере сайдбара sent/opened ещё считаются, revoked — нет
expiredБейдж «Истёк срок». Alert: срок подписи по SMS истёк, нажать «Отправить SMS ещё раз» — сообщение уйдёт на тот же номер. Кнопки «Открыть ссылку из SMS» нет даже при URL в БД (§1.4). Повтор SMS — §1.5. Fill JSON → 422 «Договор недоступен для заполнения». В каунтере сайдбара не считается
revokedНет «Заполнить» / «Подписать» / «Изменить». Если позже пришёл signed PDF (старое SMS) — «Скачать подписанный» (и «Скачать PDF» оригинала, пока статус не signed). Если в БД остался валидный provider_signing_url — кнопка «Открыть ссылку из SMS» всё ещё на карточке (§1.3). Бейдж статуса — «Отозвано», не «Подписано»

Школьная схема тех же статусов (кнопка «Памятка» на /client-contracts): анонс, contracts §4.2. Подписи «Отправлено СМС» / «Открыто СМС» — в timeline, бейдже списка и на карточке школы (Contract::schoolStatusLabel). В кабинете по-прежнему короткие подписи («Отправлено» / «Открыт» в AccountDocumentsController). Аудит и вебхуки остаются на Contract::$STATUS_RU («Отправлено» / «Открыто»). Просрочка заполнения и SMS на карточке кабинета — §1.4. Повтор SMS из кабинета — §1.5. Оставшиеся дни до срока подписания — §1.6.

4) Валидация generate

AccountContractGenerateRequest: обязательные поля по required в схеме; системные поля (contract_date, contract_id, legal_entity_*…) не показываются родителю. Форма с novalidate, без HTML5 required (звёздочка в label остаётся). Ошибки валидации полей — JSON/redirect с ключами fields.{key}, подпись в тексте — как в форме (fillFormFieldLabel); в модалке выводятся под соответствующим полем (is-invalid + invalid-feedback[data-error-for]), без общего списка. Ошибка отсутствия юрлица — ключ contract, alert сверху (см. §2.5).

4.1) {{contract_date}} и разрывы Word

Поведение: ключ contract_date — fill_mode=system (пресет «Договор»). В модалке заполнения поля нет; при POST …/generate значение берётся из ContractTemplateSystemPlaceholders как now()->format('d.m.Y') и попадает в filled_data и в DOCX→PDF вместе с contract_id, documents_url и (при наличии в схеме) legal_entity_*.

Разрывы OOXML: в Word на экране видно обычный {{contract_date}}, но файл может хранить { и { в разных w:t. Подстановка — DocxPlaceholderSupport / ContractDocxPlaceholderFiller — учитывает такие разрывы и заменяет все вхождения. Подробности и тесты — contract-templates §6.2.

Уже скачанный PDF после правки шаблона/кода сам не меняется: нужна повторная генерация (кнопка изменения данных в статусе draft при доступном edit-окне, либо новый договор).

Лишние переносы строк в PDF на драйвере phpword (типичный прод без proc_open): Word-нумерация абзаца (w:numPr) → PhpWord режет run’ы на отдельные <p>. Конвертер снимает нумерацию с рабочей копии перед загрузкой. Подробно: contract-templates §8.1.
  • AJAX generate → JSON { message, poll }; 422 не перезагружает форму: errors['fields.{key}'] мапятся в [data-error-for] под полями; errors.contract — alert сверху.
  • Non-AJAX POST → 302 на index с ?fill={id}, flash success; PDF на диске, статус draft.
  • Guest → login; без account.documents.view → 403; договор sibling семьи → как свой; чужой (не владелец и не sibling) → 404 (contract.owner / canAccessContract).

5) Скрытое право «показывать ключи полей»

Право account.contracts.showFieldKeys (скрытое в БД, не в базовых ролях): при наличии под полем показывается технический ключ {{…}} из DOCX.

6) Приглашение по email

При создании договора по шаблону (ContractCreationService::notifyClientAboutFill) уходит ContractClientFillInvitationMail на непустые адреса ученика (users.email) и родителя (parents.email). Если адреса совпадают (после trim, без учёта регистра) — одно письмо. Если разные — два отдельных письма с одним текстом (не одно письмо с двумя To). Есть только один адрес — одно письмо. Оба пустые — договор создаётся, писем нет. Сбой SMTP на одном адресе не отменяет отправку на второй. Текст берётся из версии шаблона (email_subject, email_body_html) или системных дефолтов (ContractTemplateEmailDefaults); плейсхолдеры подставляет ContractInvitationEmailRenderer ({{child_full_name}}, {{partner_name}}, {{documents_url}}, {{fill_deadline}}, {{contract_id}}). В письме {{documents_url}} = /account-settings/documents?student={contract.user_id}&fill={contract.id} (ребёнок договора + автооткрытие модалки). В PDF тот же ключ остаётся общим /account-settings/documents без query (ContractTemplateSystemPlaceholders). Режим PDF приглашение не шлёт. Анонс: /doc#contract-invitation-parent-email-index, семейная ссылка: /doc#account-documents-family-link-index.
