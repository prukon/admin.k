ЗП тренеров

Файл: /docs/documentation/schedule-trainer-salary.html · страницы: GET /schedule/trainer-salary (schedule.trainer-salary), GET /schedule/trainer-salary/data (schedule.trainer-salary.data)
Не путать с «Расписание школы» (слоты абонементов).
Расчёт строится из актуальных событий статуса «Посетил» с тренерами в pivot user_lesson_occurrence_status_event_trainers (контур user_lesson_occurrence_status_events журнала / календаря) — так же, как «Нагрузка тренеров». Каждому выбранному тренеру идёт отдельный зачёт тренировки. См. журнал §6.
Вкладка «ЗП тренеров» в разделе «Журнал расписания» (оболочка resources/views/admin/schedule/index.blade.php).
За календарный месяц ведётся черновик в БД (autosave). Кнопки «Расчет» (в строке итога блока тренера) и «Сформировать всех» создают версионные слепки — их архив на вкладке «Листы ЗП».

1.1) Схемы расчёта

Модуль ЗП — общее ядро (период, черновик, слепки, листы) плюс изолированные схемы. У партнёра в один момент одна схема на всю школу. Каталог: classic (право schedule.trainerSalary.scheme.classic) и kansas (право schedule.trainerSalary.scheme.kansas). Схема партнёра определяется по permission_role (есть ли право схемы у любой роли этого партнёра); при двух выданных правах побеждает первая в реестре (classic, затем kansas).

На вкладке ЗП переключателя схемы нет. Superadmin включает схему в матрице «Настройки → Права и роли» (/admin/settings/rules), группа «Расписание»: скрытые права «ЗП тренеров: схема «Классическая»» и «… схема «Канзас»» (видны только superadmin). Галочка у роли школы (обычно admin) включает схему партнёру. Сотрудникам для работы вкладки нужны schedule.trainerSalary.view и при правке manage. Superadmin видит модуль и без выдачи схемы: fallback — classic (Gate::before + TrainerSalaryAccess).

Файлы classic: app/Services/Schedule/TrainerSalary/Schemes/Classic/, kansas: app/Services/Schedule/TrainerSalary/Schemes/Kansas/, таблицы UI — resources/views/admin/schedule/trainer-salary/{classic|kansas}/. Ядро: TrainerSalaryService, TrainerSalarySchemeRegistry, TrainerSalarySchemeResolver, TrainerSalaryAccess.

1.3) Смена схемы месяца без слепка

Период хранит scheme_code. Пока за месяц нет ни одного слепка (кнопка «Расчет» хотя бы у одного тренера или «Сформировать всех»), период следует текущей схеме партнёра. Триггеры пересборки: GET страницы, GET …/data (фильтр месяца), PATCH черновика, POST слепка (TrainerSalaryService::ensurePeriod → rebaseUnlockedPeriodToActiveScheme). Если право сменили (classic → kansas или наоборот), scheme_code обновляется, черновик старой схемы удаляется (discardUnlockedDraft), поля не переносятся (оклад/бонусы/X/база). Визиты журнала не трогаются: после перехода на Канзас под тренерами появляются группы, где были «Посетил». Повторное открытие уже совпадающего месяца черновик не сбрасывает (X остаётся). Другой месяц не наследует X и базы.

Смотреть вкладку без manage тоже переключает незафиксированный месяц (GET вызывает ensurePeriod). Гость (редирект/401) и сотрудник без схемы (403) период не меняют. Если выданы обе схемы — unlocked-месяц становится classic.

После первого слепка схема месяца фиксируется целиком (достаточно слепка одного тренера): смена права не пересчитывает этот месяц и не трогает листы ЗП. Новый месяц открывается уже по текущему праву.

3) Справочник: оклад и ставка по умолчанию

Схема classic — карточка тренера: default_base_salary_cents, default_rate_per_training_cents (trainer_profiles; канон — money). При первом появлении тренера в черновике classic копирует оба значения в trainer_salary_draft_lines.

Схема kansas — тип тренера: оклад за тренировку и базовая премия живут в trainer_types, на человеке — только trainer_type_id. Черновик всегда равен актуальному типу (в таблице ЗП эти две суммы readonly). Слепки не пересчитываются. Поля профиля default_* Канзас не читает.

5) Кто попадает в таблицу

Активные тренеры партнёра (TrainerSalaryService::activeTrainersForPartner):

  • trainer_profiles.is_enabled = true;
  • связанный users.is_enabled = true;
  • сортировка: sort_order, затем id.

Отключённый тренер или пользователь в таблице ЗП не показывается; существующая строка черновика при отключении не удаляется автоматически.

6) Кол-во тренировок (classic)

В схеме classic совпадает с итогом по строке тренера в «Нагрузке тренеров» при режиме «без групп» (суммы по дням недели): один календарный день может учитываться дважды, если в этот день были визиты учеников из разных групп с одним тренером.

Это не колонка журнала /schedule (schedule-journal §5.3, анонс /doc): там считается число занятий ученика за месяц со статусом consumes_lesson, а не тренировки тренера.

Сервис: TrainerWorkloadReportService::trainerRowTrainingsTotals($partnerId, $dateFrom, $dateTo) — вызывается при buildReport и перед формированием слепка. Канзас считает иначе (слот + дата) — §12.

7) Формула итого (classic)

total_cents = base_salary_cents + (trainings_count × rate_per_training_cents) + bonuses_cents − deductions_cents

Расчёт только на сервере: App\Services\Schedule\TrainerSalary\Schemes\Classic\ClassicTrainerSalaryCalculator — целочисленная арифметика в копейках (без float/bc*).

Пример: оклад 10000,00 ₽ (1 000 000 коп.), 3 тренировки × 300,00 ₽ → сумма за тренировки 900,00 ₽, итого 10900,00 ₽.

8) UI и фронтенд

  • Шаблон оболочки: resources/views/admin/schedule/trainer_salary.blade.php; таблицы: resources/views/admin/schedule/trainer-salary/{classic|kansas}/_table.blade.php.
  • Подзаголовок вкладки у classic — «кол-во как в нагрузке» (TrainerSalaryScheme::draftSubtitle()). У kansas подзаголовка нет.
  • Скрипт и стили вкладки — hotfix public/js/trainer-salary.js (копия resources/js/trainer-salary.js) и public/css/trainer-salary.css. Vite-бандл на этой вкладке не подключается (npm run build для выкладки hotfix не требуется).
  • Фильтр «Период» — input type="month"; смена месяца → GET …/data, обновление URL query (year, month).
  • При manage: autosave черновика по change полей (debounce 400 мс) → PATCH …/draft/{id}; ошибки 422 — под соответствующим полем (data-error-for). Classic обновляет одну строку из JSON row. Kansas всегда отвечает reload_table: true + полный table_html (X и базовое среднее общие; иначе в DOM обновился бы только один тренер). X и «Баз. среднее» правятся в модалке «Настройки месяца»; клиент шлёт team_id из data-team-id строки группы в модалке. После PATCH таблица пересобирается, поля модалки не затираются (фокус остаётся). Смена месяца обновляет и month_settings_html.
  • Кнопка «Расчет» → POST …/snapshots/{id}: у classic — в строке тренера, у Канзаса — в подвале блока сразу слева от «Итого:». Под именем тренера — подсказка «Слепок vN · дата · кто сформировал».
  • «Сформировать всех» — confirm, затем POST …/snapshots; создаёт слепок для каждого активного тренера с одним batch_id.
  • При Канзасе и manage: кнопка «Настройки месяца» (рядом с «Типы тренеров») открывает модалку в стиле журнала «Статус занятия» (schedule-modal-content cell-edit-modal, стандартная ширина, заголовок «Настройки базовых значений за {месяц}»): базовая надбавка к премии на школу за этот месяц и базовое среднее всех активных групп партнёра. X в поле — целое, копейки в ховере. Базовое среднее — только целое, без ховера и без десятых. Кнопка «Типы тренеров» открывает ту же модалку, что на /admin/trainers (hotfix public/js/trainer-types.js). После сохранения типа таблица ЗП пересобирается; простое открытие модалки (reason === 'open') таблицу не трогает.
  • Без manage: поля readonly, кнопки «Расчет» нет, кнопок «Сформировать всех», «Настройки месяца» и «Типы тренеров» нет. У Канзаса надбавка показывается текстом над таблицей.

9) Бэкенд

  • Контроллер: ScheduleTrainerSalaryController.
  • Ядро: TrainerSalaryService — период, слепки, партнёрский скоуп, смена схемы без слепка. Конкретная схема (classic / kansas) синхронизирует строки, считает тренировки, валидирует PATCH и рисует таблицу.
  • Запросы: TrainerSalaryReportRequest (view + схема), UpdateTrainerSalaryDraftLineRequest (правила полей — у схемы), FormTrainerSalarySnapshotRequest (manage + схема; authorize + rules + messages).

9.1) Ответ GET …/data

JSON: year, month, month_label, date_from, date_to, scheme_code, draft_subtitle, draft_view_data, table_view, can_manage, table_html, month_settings_html (Канзас+manage: тело модалки настроек месяца; иначе пустая строка), rows[].

Элемент rows[]: trainer_profile_id, trainer_name, у kansas ещё trainer_type_name (название типа в скобках в шапке), денежные поля строкой "NNNN.NN", trainings_count, comment, latest_snapshot (или null: id, version, batch_id, scheme_code, formed_at, formed_by_name, total). У kansas в строке тренера есть groups[]; в draft_view_data — premium_increment (X в рублях), premium_increment_int, month_settings_title, month_groups[] (активные группы: team_id, team_title, base_avg_students, base_avg_students_int), save_trainer_id (для PATCH из модалки).

10) Версии слепков

  • «Расчет» по тренеру: version = max(version) + 1 в рамках периода и тренера; batch_id = null. Этого слепка достаточно, чтобы зафиксировать схему месяца (§1.3).
  • «Сформировать всех»: для каждого активного тренера слепок v1 (или следующая версия, если уже были одиночные слепки), общий batch_id (UUID).
  • Слепок фиксирует все поля строки на момент формирования; черновик после этого можно менять — новый слепок возьмёт актуальный черновик.

Autosave черновика (PATCH) и формирование слепков (POST) при успехе всегда отвечают JSON (message, сущность), в том числе без заголовка X-Requested-With: запись сохраняется, тело не пустое, не 500 и не «голый» 200. Ошибка валидации: AJAX/patchJson → 422 errors[field]; обычный браузерный PATCH без JSON Accept → 302 + session errors[field] (запись не меняется). Для Канзаса успешный PATCH/POST дополнительно отдаёт reload_table: true и полный table_html (плюс month_settings_html). Клиент подменяет только таблицу: тело модалки настроек месяца после PATCH/POST не пересобирается, чтобы не сбросить незавершённый ввод и фокус. Смена фильтра месяца (GET …/data) обновляет и таблицу, и month_settings_html (заголовок «за {месяц}»).

12) Схема «Канзас» (kansas)

В таблице на строке группы показываются оклад за тренировку и базовая премия — они берутся из типа тренера и в ячейках ЗП readonly (править в модалке «Типы тренеров»). В шапке блока тренера — имя и тип в скобках. Итог тренера и кнопка «Расчет» — внизу блока, сразу слева от подписи Итого: и суммы (trainer-salary-kansas-foot). Человек всегда равен актуальному типу: черновик переписывается, слепки не меняются. Редактируемые поля месяца живут в модалке «Настройки месяца» (кнопка при manage, заголовок «Настройки базовых значений за {месяц}», стиль журнала schedule-modal-content cell-edit-modal): базовая надбавка к премии — одно значение на школу за выбранный месяц (у каждого месяца своё); базовое среднее учеников — на каждую активную группу партнёра (is_enabled), не только у тех, где были визиты. В модалке X показывается целым, копейки — в ховере. Базовое среднее — только целое, без ховера (step="1"). В таблице «Баз. среднее» / факт / разница — readonly, целое, без ховера. Без manage кнопки настроек нет; надбавка над таблицей — текст.

Строка группы — отдельная строка таблицы и появляется, только если в выбранном месяце у тренера есть занятие со статусом «Посетил» (pivot тренеров). Тренер без таких визитов в таблицу не попадает (в JSON rows он остаётся, в table_html нет). Имя — в шапке блока вместе с типом тренера в скобках; итог и «Расчет» — в подвале (trainer-salary-kansas-foot, подпись Итого:). Если ни у кого нет визитов — «Нет тренеров с тренировками в этом месяце». Базовое среднее — целое (16); дробь (16.5, 16.55) → 422 errors.base_avg_students. Фактическое среднее: round(сумма / тренировки, 1), затем вверх до целого (15.04 → 15, 15.1 → 16). Это целое идёт и на экран, и в формулу; исходная дробь нигде не хранится. Колонки *_tenths хранят целое × 10 (16 → 160). Сохранение по change; правка базы подставляется всем тренерам этой группы. PATCH «Баз. среднее» шлёт team_id вместе с base_avg_students (клиент берёт data-team-id строки группы в модалке).

Поля PATCH Канзаса (рубли в HTTP, в БД *_cents; средние — целые ученики, в колонках *_tenths как ×10): premium_increment (X) — на школу за месяц; base_avg_students + team_id — на группу. rate_per_training и base_premium в PATCH запрещены (422): задаются в типе тренера. Оклад classic / бонусы / вычеты в UI Канзаса нет (base_salary_cents = 0 в строке ядра).

Тренировка существует, если в занятии (слот + дата) хотя бы один ученик имеет актуальный статус «Посетил» с этим тренером (тот же контур, что нагрузка: latest user_lesson_occurrence_status_events + pivot тренеров). Идентичность тренировки: (trainer, team_id, team_schedule_slot_id, occurrence_date) — два слота в один календарный день считаются двумя тренировками (в отличие от COUNT(DISTINCT DATE) нагрузки). Численность занятия — DISTINCT user_id. Фактическое среднее = сумма численностей / число тренировок группы, затем округление до десятой и вверх до целого — §12.1. В таблицу групп попадают только группы, где у тренера были такие визиты в месяце. Если у слота нет team_id, строка называется «Без группы» (team_id = 0).

12.1) Целые средние

Анонс: /doc#trainer-salary-kansas-integer-averages-index. Код: KansasQuantity::averageToTenths (факт: десятая, затем вверх до целого; 151/10 → 16), toWholeTenths (база: только целое), UI без ховера на средних. 

fact_avg = ceil(round(sum / trainings_count, 1))   // 15.04 → 15, 15.1 → 16
diff = fact_avg − base_avg                         // оба целые
premium_per_training = max(0, base_premium + diff × X)
pay_per_training = rate_per_training + premium
group_total = pay_per_training × trainings_count
trainer_total = sum(group_totals)

Средние в UI и формуле — целые ученики. В БД колонки *_tenths хранят целое × 10 (16 → 160), чтобы премия считалась через то же деление на 10, что и деньги в копейках. JSON groups[] отдаёт целое в base_avg_students / fact_avg_students / diff_students и те же значения в *_int (не "16.0"). Ховер у средних нет. У X (надбавка к премии) ховер с копейками остаётся (step="0.01"). База в модалке — step="1"; дробь (16.5, 16.0) → 422 errors.base_avg_students (non-AJAX без JSON Accept → 302 + session). Classic это правило не получает. Слепок замораживает уже целое. Money / копейки / формула премии не менялись: меняется только то, какие целые идут в diff. После подмены table_html / тела модалки клиент вызывает KidsCrmTooltip.dispose/init(..., { scopes: ['hint'] }) (ховер X).

Пример: оклад 1000, базовая премия 800, X 100; группа A база 16 факт 14, 10 тренировок → премия 600, за тренировку 1600, группа 16 000; группа B база 18 факт 25 → 1500 / 2500 / 25 000; тренер 41 000.

Данные Канзаса изолированы: trainer_salary_kansas_period_settings (X), trainer_salary_kansas_group_baselines (базовое среднее группы), trainer_salary_kansas_draft_trainers / _draft_groups, trainer_salary_kansas_snapshot_trainers / _snapshot_groups (заморозка при слепке). На trainer_salary_draft_lines.total_cents — итог тренера (для списка листов).

Клиент: вкладка грузит hotfix public/js/trainer-salary.js и public/css/trainer-salary.css (не Vite-бандл). Успешный PATCH/POST Канзаса возвращает reload_table: true и полный table_html (плюс month_settings_html) — иначе смена X или базового среднего обновила бы только строку тренера, с которого ушёл запрос. Клиент после PATCH/POST подменяет только таблицу; тело модалки не затирается. Смена месяца применяет month_settings_html. При первом открытии месяца X = 0, оклад за тренировку и базовая премия — из типа тренера (системный тип «Главный тренер», суммы с нуля, пока их не задали); другой месяц не наследует X и базы. Смена classic ↔ kansas без слепка — §1.3.
