Партнёры: базовые роли и права по умолчанию

Файл: /docs/documentation/partners-permissions.html
Цель: при создании нового партнёра (школы) автоматически назначать базовые permissions системным ролям user, admin и trainer в рамках этого партнёра.

1) Как устроены роли/права (важно)

  • Системные роли: roles.name = user/admin/trainer существуют один раз в системе (общие для всех партнёров). Роль user в матрице и ЛК — UI-label «Клиент» (вкладка «Клиенты»); roles.name не меняется. Роль trainer отображается в матрице ролей (is_visible = 1) и как вкладка «Тренеры» в разделе «Пользователи»; участвует в автопроставлении прав наравне с user и admin.
  • Права: permissions — единый справочник имён permissions. В матрице «Права и роли» права сгруппированы по permission_groups (см. группы в матрице).
  • Назначение прав ролям делается в разрезе партнёра через pivot-таблицу permission_role:
    • permission_role.partner_id
    • permission_role.role_id
    • permission_role.permission_id
Это не “классический” Spatie-permission по умолчанию (где role_has_permissions глобальный). В kidscrm права роли могут отличаться между партнёрами, поэтому ключевой контекст — partner_id.

2) Источник истины: конфиг базовых прав

Списки базовых permissions для ролей user, admin и trainer живут в конфиге:
/config/role_base_permissions.php
  • Почему конфиг: один источник правды для модели (автопроставление), сидеров и тестов.
  • Важно: если включён config:cache, после деплоя нужно обновить кеш конфигов.

3) Автопроставление при создании партнёра

Реализация сделана “прямо в модели” партнёра:
/app/Models/Partner.php (хуки creating и created в booted()).

3.1 Fail-fast в creating (без “полупартнёра”)

  • Перед вставкой партнёра проверяем, что все permissions из конфига реально существуют в permissions.
  • Если чего-то нет — бросаем RuntimeException и создание партнёра прерывается (строка в partners не появится).

3.2 Назначение в created

  • Для нового partner_id берём:
    • role_id для ролей user, admin и trainer
    • permission_id по спискам имён из конфига
  • Вставляем строки в permission_role пачкой (bulk insert) и идемпотентно через insertOrIgnore.

4) Ограничение на дубли: UNIQUE по тройке

В permission_role должен существовать уникальный индекс на: (partner_id, role_id, permission_id).
  • Это гарантирует отсутствие дублей и корректную идемпотентность.
  • Добавлена миграция-страховка: /database/migrations/2026_02_19_000001_ensure_permission_role_unique_triplet.php (для MySQL/MariaDB, с дедупликацией при необходимости).

5) Сидеры базовых прав (dev/test сценарии)

Сидеры используют тот же конфиг и заполняют permission_role для всех партнёров в БД (только при SEED_DEV_DATA=true):

7) Права, которые не входят в базовый набор admin

В config/role_base_permissions.php для роли admin при создании партнёра не проставляются (нужно включить вручную в «Права и роли» / superadmin):
  • setPrices.customPayments.view — доп. платежи: вкладка, консоль, создание, редактирование суммы/описания, удаление неоплаченного; у user тоже не в базовом наборе — setting-prices-custom-payments, /doc;
  • setPrices.manualPaid.manage — ручная отметка оплаты месяца (карандаш на «По месяцам» / «По ученикам») и селект статуса доп. платежа (не кнопка «Редактировать»); на «По месяцам» unpaid→paid ещё абонемент/сумма из карточки — анонс; не в базовых ролях — setting-prices-monthly-users;
  • inAppNotifications.manage — зарезервировано под создание in-app рассылок админом школы (v1 UI формы нет: создаёт только superadmin). Скрытое; не в базовых ролях. Просмотр колокольчика — inAppNotifications.view, оно в базовых ролях — in-app-notifications. Чат — messages.view, тоже в базовых ролях (chat);
  • setPrices.packageAssignments.view — назначения абонементов (вкладка админки); нужно вместе с lessonPackages.view — set-prices-package-assignments;
  • scheduleSlots.view / scheduleSlots.manage / scheduleSlots.table / lessonPackages.export / lessonPackages.manualPaid.manage — группа «Расписание школы» (schoolSchedule): пункт меню, слоты, вкладка «Таблица занятий», Excel, ручная оплата назначения; scheduleSlots.view также закрывает автосписание / заморозку / срок в модалке и колонках таблицы шаблона. Все шесть прав группы (включая setPrices.packageAssignments.view) скрытые (is_visible=0); новым партнёрам не выдаются; существующим школам миграция выдачу не снимает — анонс, settings-permission-groups, school-schedule-calendar;
  • setPrices.cabinetPackages.fixed.view / .flexible.view / .single.view / .postpay.view — отображение типов абонементов на консоли; скрытые; не в базовых ролях — set-prices-cabinet-packages;
  • platformPayments.method.yookassa — ЮKassa на кошельке и абонплате CRM; скрытое; не в базовых ролях. T‑Bank СБП платформы (platformPayments.method.tbankSbp) в базовой роли admin только для новых школ; существующим миграция не выдаёт — partner-wallet §8, анонс прав, анонс эквайринга;
  • lessonPackages.type.fixed / .flexible / .no_schedule / .postpay — выбор типа шаблона абонемента; скрытые; UI option + store/update + выбор в «Установка цен», ULP и уведомлениях; миграции никому не выдают (у admin строки в конфиге закомментированы); lesson-packages-type-permissions, анонс, postpay — lesson-packages-type-postpay, postpay;
  • users.full_name_genitive — ФИО ученика в родительном падеже (CRM / ЛК / колонка импорта Excel); скрытое (is_visible=0); по умолчанию никому; договоры {{child_full_name_genitive}} работают независимо — admin-users §2.1.7;
  • reports.payments.commission_total.view — отчёт «Платежи»: колонка «Комиссия» (сводно); скрытое (is_visible=0); не в базовых ролях; строка в конфиге закомментирована; миграция hide не трогает permission_role — reports-payments, анонс /doc;
  • account.user.team.update — ЛК: добавление группы (сайдбар «Группа: … изменить», карандаш на /cabinet и /account-settings/user/edit; только attach); скрытое (is_visible=0); не в базовых ролях; миграция revoke с ролей; после успешного attach — колокольчик admin/trainer школы (текст: с родителем — «Родитель / Ребёнок / Добавлена группа», иначе «{ФИО} добавил группу»; событие, текст, dashboard-cabinet §7.1);
  • messages.threads.delete — корзина в шапке чата (soft-delete лички и ручной группы, не авто-чат threads.team_id); скрытое (is_visible=0, группа mainMenu); не в базовых ролях; superadmin видит через Gate::before; chat §2.8, анонс /doc;

8) Роль trainer и право trainers.view

Роль trainer в конфиге получает ограниченный набор (личный кабинет, профиль, просмотр партнёра) — без доступа к админским отчётам и CRUD пользователей. Роль admin по умолчанию включает trainers.view (раздел «Тренеры», фильтр в отчётах, привязка к группам). Право groups.own («Только свои группы») в базовый набор trainer и admin не входит — школа включает его роли тренера в матрице. Без права тренер с рабочими правами видит все группы школы. Подробно: groups-own, анонс /doc. Подробно: Тренеры (админка).

9) Заявки с сайта (виджет и лендинг)

Для роли admin в конфиге заданы schoolLeads.view и schoolLeadLanding.view (список заявок клиентов школы и вкладка «Страница заявки» / /admin/school-leads/landing). Право schoolWidget.view (вкладка «Виджет для сайта», embed-код / Telegram) в базовый набор не входит — назначается отдельно (оба права с is_visible = 0, в матрице видны superadmin). Это не то же самое, что partnerLeads.view (B2B-лиды платформы). Подробно: Заявки с сайта (виджет и CRM), страница заявки партнёра.

10) Кастомные роли в админке

Отдельный сценарий: администратор создаёт новую (несистемную) роль на вкладке «Права и роли». Стартовый набор прав для такой роли берётся из того же конфига, ключ roles.admin, но логика и ограничения отличаются от сидеров и от автопроставления при создании партнёра — см. Настройки: кастомные роли и стартовый набор прав.
