Установка цен → «По месяцам» и «По ученикам»

Файл: /docs/documentation/setting-prices-monthly-users.html. CRM: /admin/setting-prices/monthly, /admin/setting-prices/users (вкладки в admin/SettingPrices/index).
Кратко. Раздел задаёт и показывает месячные начисления users_prices в разрезе группы (team_id). С 2026‑08 обе вкладки умеют показывать историю учеников, которых уже нет в группе (бывшие участники), но не дают менять абонемент и цену. На «По месяцам» неоплаченное начисление бывшего снимается корзиной (§3.2.1, анонс). Источник истины по членству — pivot team_user (student-team-membership); модель данных начислений — payments § users_prices.

Постоплата: в select абонемента тип postpay доступен при праве lessonPackages.type.postpay — сумма = посещения × цена занятия, затем скидка по снимку строки, без записи в user_lesson_packages. Для остальных типов (fixed / flexible / no_schedule) при сохранении users_prices.lesson_package_id сервис UsersPriceLessonPackageSync создаёт/обновляет связанный ULP — подробно в § ULP sync. Предоплату можно заменить на другую предоплату даже если месяц разложен в журнале или уже оплачен (сумма оплаченного заморожена) — анонс. На оплаченный месяц без абонемента можно поставить предоплату (сумма заморожена, ULP создаётся оплаченным, журнал не трогаем) — анонс. Сумму > 0 без абонемента сохранить нельзя (исторические строки при том же payload остаются) — анонс. На вкладке «по месяцам»: слева при postpay цена группы скрыта (иконка i с подсказкой), справа сумма только расчётная (0 при 0 посещений). Кнопка «Применить» слева назначает шаблон. Без права новые postpay в каталоге скрыты (уже назначенные остаются для отображения); новый выбор → 422 на поле пакета. Подробно — postpay, lesson-packages-type-postpay.

Персональная скидка ученика: «Применить» слева копирует каталожную цену группы без иконки %; у учеников справа сумма = каталог × % карточки, на строке пишется снимок. Постоплата: после «посещения × ставка» применяется % снимка строки. Анонс — /doc, карточка — admin-users §2.6.

Уведомления об оплате: отдельная вкладка /admin/setting-prices/notifications (право setPrices.paymentNotifications.manage) — конструктор email-правил по неоплаченным users_prices — setting-prices-payment-notifications.

Ручная оплата и абонемент в карточке: на «По месяцам» смена статуса «неоплачено → оплачено» сохраняет выбранный в селекте абонемент и сумму (apply до флажка is_manual_paid). Анонс — /doc, подробно — §4.0.

Выбор группы на «По месяцам»: оранжевая плашка слева появляется только вместе со списком учеников справа (пульс строки без спиннера у селекта, справа «Загрузка…»). Анонс — /doc, подробно — §3.2.

Корзина бывшего на «По месяцам»: вместо карандаша — снять неоплаченное начисление (обнулить сумму, снять абонемент, ULP если не разложен). Оплаченное без корзины. Право setPrices.view, не manualPaid.manage. Вкладка «По ученикам» корзины не показывает. Анонс — /doc, подробно — §3.2.1.

Ручная пролонгация месяца: на «По месяцам» кнопка копирует абонементы M → M+1 по всем группам партнёра (превью, затем подтверждение). Это не classic-автопролонг назначений и не вкладка «По ученикам». Анонс — /doc, подробно — §4.2.

0) Sync users_prices ↔ ULP (assignable-пакеты)

Зачем. Партнёры, работающие только в «Установке цен» + журнале (без UI «Расписание школы»), должны получать кнопку «+» в журнале после назначения fixed-пакета. До sync в users_prices стоял только lesson_package_id, без строки ULP — «+» не появлялся.

0.1) Когда создаётся / обновляется ULP

  • Триггеры: setPriceAllUsers, setTeamPrice / снимок ученикам группы, user-year-prices/save, setManualPaid при mode=paid с lesson_package_id / price из карточки (до флажка оплаты), и аналогичные пути apply в контроллере.
  • Типы шаблона: fixed, flexible, no_schedule (LessonPackage::ASSIGNMENT_SCHEDULE_TYPES). Postpay → ULP не создаётся.
  • При создании assignable-пакета: billing_month = users_prices.new_month, ends_at = последний день месяца; для flexible сразу starts_at = 1-е число месяца (занятия ставят «на лету» в журнале); для fixed / no_schedule — starts_at = NULL до раскладки, fee_amount_cents = цена месяца (копейки; в HTTP/JSON — fee_amount / price в рублях), объём = lessons_count шаблона, FK users_prices.user_lesson_package_id.
  • duration_days шаблона для месячного ULP не задаёт период (скрыть поле в модалке и колонку таблицы без scheduleSlots.view это не меняет — lesson-packages §Срок действия, анонс).

0.2) Правила изменений

  • Смена суммы при неразложенном / даже разложенном ULP (если месяц и ULP не оплачены) → синхронизация fee_amount_cents (из рублей UI через Money).
  • Смена шаблона при уже разложенном ULP (isLaidOutInSchedule): предоплата → предоплата (тот же месяц/группа, та же строка ULP) разрешена: объём и остаток пересчитываются (consumed = max(ledger, события consumes_lesson), ячейки «Запись» не считаются); новый объём < списанного → 422 на поле пакета, ничего не пишем; журнал сами не дополняем. Иные типы (fixed / разовое / postpay) при раскладке → 422 (текст про раскладку в расписание). Анонс — /doc#setting-prices-flexible-replace-index.
  • Смена шаблона при неразложенном → обновление ULP (объём/пакет).
  • Снятие пакета / уход на postpay → физическое удаление неразложенного ULP; если разложен → 422.
  • Оплаченный месяц (users_prices.effective_is_paid или оплаченный ULP): сумму не переписываем; шаблон можно сменить предоплата → предоплата или назначить предоплату на месяц без абонемента (пусто → предоплата): создаётся оплаченный ULP с суммой месяца и полным объёмом шаблона; журнал (пробные / разовые) не привязываем. Снять пакет / поставить не-предоплату → 422 на поле пакета («Нельзя снять абонемент у оплаченного месяца.» / «На оплаченный месяц без абонемента можно поставить только абонемент предоплаты.» / «Сменить оплаченный абонемент можно только на другой абонемент предоплаты.»). Снимок тарифа слева ставит предоплату и оплаченным без абона; оплаченный фиксированный / постоплата по-прежнему пропускает молча.
  • Неоплаченная замена с новой суммой: отмена активного T‑Bank QR месяца (/pm/{code} живой) и перевыпуск SMS /p/{code} (payments §3.4.1, §3.1.3).
  • Автопролонгация: если у ученика есть ULP с auto_prolong_enabled, создание нового месячного ULP через sync → ошибка с UserLessonPackageAutoProlongGuard::BLOCK_REASON (см. lesson-packages §auto-prolong). Месячные ULP из установки цен сами автопролонгацию не поддерживают.
  • Идемпотентный догон: повторный Apply с теми же значениями снова вызывает sync — создаёт отсутствующий ULP и/или чинит ends_at у неразложенного месячного назначения (для flexible также starts_at = 1-е число месяца, если ещё нет UTSS). Исторический backfill всех старых месяцев не делается.

Сервис: App\Services\SettingPrices\UsersPriceLessonPackageSync. Раскладка fixed в журнале (только месячные: группа→абонемент, team_locked) — schedule-journal §7; занятия из абонемента предоплаты — §7.3. Модель периода — lesson-packages § billing_month.

3) Бывшие участники группы (новый функционал)

Зачем. Ученик мог оплатить месяц в группе «Алмаз», затем быть переведён в «Дубль». Начисление в users_prices остаётся, но без pivot в «Алмаз» старый UI его не показывал. Теперь история видна на обеих вкладках только для просмотра.

3.1) Кто считается «бывшим»

  • Ученик не состоит в выбранной группе по team_user (в т.ч. после soft-delete группы ученики отвязываются от pivot — см. student-team-membership §1.2).
  • Есть история начислений с users_prices.price_cents > 0 по этой группе (критерий зависит от вкладки — ниже).
  • Отключённый ученик (is_enabled=0), ещё состоящий в pivot, на вкладке «по месяцам» не показывается ни как текущий, ни как бывший (как и раньше: в список месяца попадают только is_enabled=1 из pivot).

Хелпер: UserPriceTeamMembership::studentHasPositivePriceHistoryForTeam($userId, $teamId).

3.2) Вкладка «По месяцам»

  • Endpoint: POST /admin/setting-prices/get-team-price (getTeamPrice) — JSON.
  • Выбор группы: оранжевая плашка wrap-team--active ставится только после успешного ответа, вместе со списком справа. Vite-модуль: openTeamDetail только вызывает loadTeamUsersRightColumn (плашку и lastTeamId не трогает). Между кликом и ответом — wrap-team--loading (пульс строки, без спиннера у селекта) и плейсхолдер «Загрузка…» в .wrap-users. HTTP-ошибка AJAX — плашку не ставить, правую колонку очистить с текстом ошибки (кроме keepActiveHighlight после «Применить»: плашку оставить). Повторный клик отменяет предыдущий запрос (abort). Нет текущих и нет бывших (200 + success: false) — не ошибка: плашка ставится, список пустой. Только бывшие с price_cents > 0 — success: true, список бывших. После «Применить» слева/справа — keepActiveHighlight: true (плашку не снимать, loading только справа). Первый HTML: .wrap-users пустой, «Применить» справа disabled, ни одна строка без wrap-team--active. HTTP: нет teamId / selectedDate → 422 errors.teamId / errors.selectedDate (GetTeamPriceRequest, в т.ч. non-AJAX). Чужая/нет группы → 404 JSON success: false, message: Team not found (не 500). Тело — JSON или form-urlencoded (оба читаются Request). Вкладка «По ученикам» этот loading не использует: там плашка по-прежнему на клике. Анонс — /doc#setting-prices-monthly-team-select-index.
  • Текущие: активные ученики группы → UserPrice::firstOrCreate по (user_id, team_id, new_month), флаг is_former_member=false.
  • Бывшие: существующие строки за этот же месяц с price_cents > 0, user_id не в pivot группы; firstOrCreate не вызывается; флаг is_former_member=true и в usersTeam, и в usersPrice.
  • Порядок: сначала текущие (ФИО), затем бывшие (ФИО).
  • UI: бейдж «не в группе», поля абонемента/цены disabled+readonly, без карандаша. Неоплаченное начисление — корзина (§3.2.1). «Применить» справа не отправляет бывших в payload (сервер всё равно пропускает не-членов через studentBelongsToTeam). Успех карандаша одного ученика («Изменения сохранены.») и «Применить» справа («Цены ученикам в выбранной группе успешно обновлены.») — toast window.showToast в Vite-модуле resources/js/settings-prices.js (вкладка его подключает через @vite; public/js/settings-prices.js вкладка не грузит). «Применить» слева (всем группам) по-прежнему модалка успеха с reload. Анонс — /doc.
  • Пустая группа: если текущих нет, но есть бывшие с price_cents > 0 за месяц → success: true (раньше было false).
Не меняют строки бывших: setTeamPrice / setPriceAllTeams (снимок только по $team->students()), setPriceAllUsers (skip без членства), setManualPaid (422 без членства). Снять неоплаченное начисление бывшего можно только корзиной §3.2.1 (не Apply). Non-AJAX варианты apply → 302 на monthly, запись бывшего в БД не меняется.

3.2.1) Корзина неоплаченного начисления бывшего

Только вкладка «По месяцам» (/admin/setting-prices/monthly). У бывшего вместо карандаша — корзина, если месяц не оплачен (effective_is_paid = нет, ни авто is_paid, ни is_manual_paid). Оплаченное — без корзины (не disabled). Карандаш у бывшего не рисуется. Право — setPrices.view (как у раздела), не manualPaid.manage. Вкладка «По ученикам» корзины не показывает (users.blade.php без monthly Vite-модуля; user-year-prices без флагов can_clear_former_charge / former_charge_clear_block_reason). Анонс — /doc.
  • Снятие: price_cents=0, lesson_package_id=null, discount_percent / discount_comment = null, затем UsersPriceLessonPackageSync (неразложенный неиспользованный ULP удаляется). Строка users_prices остаётся. Из списка месяца пропадает (бывшие только с price_cents > 0).
  • Нельзя снять (корзина disabled, ховер kids-tooltip-hint setting-prices-monthly-clear-disabled-wrap): «Нельзя удалить: начисление уже оплачено.» (в JSON; в UI у оплаченных корзины нет); «Нельзя удалить: по постоплате уже есть посещения.»; «Нельзя удалить: связанные занятия уже стоят в расписании.»; «Нельзя удалить: по абонементу уже были занятия.». Постоплата без посещений (если строка ещё видна) — корзина активна. Клик по disabled не открывает confirm и не шлёт POST.
  • UI: класс user-price-former-clear, активная кнопка title="Удалить начисление". Подтверждение — showConfirmDeleteModal («Удаление начисления» / «Удалить начисление за {месяц} в этой группе? …»). Успех — toast «Начисление снято.» + loadTeamUsersRightColumn(..., { keepActiveHighlight: true }), без location.reload. Ошибки — .former-clear-error (поле errors.charge и др.). Vite: resources/js/settings-prices.js, POST JSON JSON.stringify + Accept: application/json (без X-Requested-With).
  • HTTP: POST /admin/setting-prices/former-month-charge/clear (ClearFormerMemberMonthChargeRequest: user_id, team_id, selectedDate; «Не указан ученик.», «Выберите группу.», «Укажите месяц.»). JSON (ajax() или wantsJson()) — 200 { success: true, message: "Начисление снято." } или 422 errors.charge / поля Request. Текущий член → 422 «Снять начисление корзиной можно только у ученика, который больше не состоит в этой группе.». Нет положительного начисления → 422 «Нет начисления за выбранный месяц, которое можно снять.». Чужой ученик / группа → 404. Non-AJAX HTML успех → 302 на monthly, запись снимается. GET/PATCH/PUT/DELETE на POST-руте → 404/405. Гость / без view → 302/401/403. Достаточно setPrices.view.
  • Оплата после снятия: /pm/{code} (и длинный /pay/up/{token}) — заголовок «Абонемент аннулирован», «Этот абонемент был аннулирован. Если у вас остались вопросы, свяжитесь с клубом.»; QR — 422 с тем же текстом. Если удалён связанный ULP — /p/{code} тоже kind=annulled. Аудит pricing.former_charge_cleared.

3.3) Вкладка «По ученикам»

  • Список (server render): активные ученики с группами в pivot или с любой историей users_prices.price_cents > 0 по группам партнёра.
  • У строки: data-team-ids (текущие) + data-former-team-ids (группы с историей price_cents > 0, которых нет в pivot). Подпись «ранее: …».
  • Фильтр группы (JS): ученик виден, если группа в текущих или в former-ids. Критерий попадания в former-ids — любой месяц с price_cents > 0 по группе (не только выбранный год справа).
  • Подробно / год: POST …/user-year-prices. Если нет членства, но есть история price_cents > 0 → 200, is_former_member=true, can_manage_manual_paid=false, все 12 месяцев read-only.
  • Save: POST …/user-year-prices/save — только при текущем членстве; для бывших 422 (и AJAX, и non-AJAX; не пустой 200). Ручная оплата — то же правило членства.
  • Заголовок справа для бывшей группы: «{группа} · не в группе».

3.3) Цена только с абонементом

Зачем. Начисление без шаблона не должно попадать в «Установку цен»: сумма > 0 сохраняется только вместе с lesson_package_id.
  • Правая колонка «По месяцам» (POST …/set-price-all-users) и вкладка «По ученикам» (POST …/user-year-prices/save). Слева (set-team-price / set-price-all-teams) абонемент группы и так обязателен («Выберите абонемент для группы.») — это правило туда не ставили.
  • Цена > 0 и нет абонемента → 422 на поле пакета, текст «Нельзя установить цену без абонемента.» под селектом (setting-prices-monthly-package-error).
  • Цена 0 + «Без абонемента» — снятие начисления, 200.
  • Историческая строка (сумма уже стоит, пакета нет): тот же payload — no-op 200; смена суммы без пакета — 422. Оплаченный месяц это правило Request не дублирует: снять пакет / поставить не-предоплату по-прежнему тексты sync («Нельзя снять абонемент у оплаченного месяца.» и т.д.). Постановка предоплаты на оплаченный месяц без абона не меняется — §0.2.
  • UI: без абонемента поле цены disabled; снятие абона на неоплаченном обнуляет сумму; оплаченный месяц при снятии абона сумму не обнуляет; после выбора шаблона подставляется каталог (кроме оплаченного). Vite «По месяцам»: «Применить» справа и карандаш; вкладка «По ученикам»: карточка месяца и «Применить» за год — оба пути шлют lesson_package_id и рисуют 422 под селектом.
  • Массовое «Применить» справа: ошибка Request на одной строке валит весь POST (в отличие от ULP-sync 422 в контроллере, где остальные строки сохраняются).
  • Ручная отметка оплаты (POST …/manual-paid) это правило не дублирует.

4.0) Ручная оплата и абонемент/сумма в карточке

На вкладке «По месяцам» смена статуса в селекте оплаты не должна терять несохранённый абонемент и сумму. Фронт (postManualPaid) при mode=paid шлёт lesson_package_id и price из DOM карточки. Бэкенд в одной транзакции вызывает applyUnpaidUserPriceRow (те же правила, что Apply справа: ULP sync, postpay, права типа шаблона) до флажка оплаты, затем пишет is_manual_paid. Если apply даёт 422 (в т.ч. errors.lesson_package_id / errors.price, разложенный не-prepaid, объём предоплаты меньше списанного) — статус не ставится. Фронт показывает тексты под селектом абонемента (setting-prices-monthly-package-error) и полем цены (setting-prices-monthly-price-error); errors.comment / errors.record — в .manual-paid-error. mode=unpaid поля карточки игнорирует (снятие оплаты не применяет абонемент/сумму). Селект абонемента у оплаченного месяца на Apply остаётся доступным (замена предоплаты — анонс; предоплата на оплаченный месяц без абонемента — анонс). Если месяц уже эффективно оплачен, applyUnpaidUserPriceRow поля карточки не применяет. Без этих полей контракт прежний: только ручная отметка. Фронт читает селект/цену из DOM карточки (JSON.stringify(payload) после if (mode === 'paid')), а не из устаревшего usersPrice в памяти. Гость / без setPrices.view / без setPrices.manualPaid.manage — 302/401/403, запись не меняется. GET/PATCH/DELETE на POST-руте → 404/405. AJAX с X-Requested-With — JSON success + user_price или 422 errors.lesson_package_id / errors.price / errors.comment. Non-AJAX POST — 302 на вкладку «По ученикам» и запись в БД (не пустой 200). Анонс — /doc#setting-prices-monthly-manual-paid-card-index.

4.2) Пролонгация на следующий месяц

Зачем. Админ один раз в месяц выставляет абонементы. Кнопка «Пролонгировать на следующий месяц» на вкладке «По месяцам» копирует шаблоны с выбранного месяца M на M+1 по всем группам партнёра. Вкладка «По ученикам» кнопку не показывает.
  • Только ручное действие: превью без записи, затем подтверждение.
  • Источник — текущий селект месяца. После успеха страница остаётся на M (toast, без reload на M+1).
  • Ученик копируется, только если он сейчас в группе (team_user, is_enabled=1) и в M у пары ученик+группа уже выбран абонемент. Пустой M, новичок без абона, бывшие участники — цель не трогаем.
  • Сумма в M+1 = текущая цена шаблона × текущий % карточки (снимок скидки с карточки, не копия суммы/снимка из M).
  • Постоплата: копируется шаблон, сумма как при apply (посещения M+1). Без права на тип шаблона (lessonPackages.type.*, для postpay — lessonPackages.type.postpay) — пропуск (type_denied / postpay_denied).
  • Assignable → UsersPriceLessonPackageSync: новый неразложенный ULP, billing_month = M+1. Раскладку журнала не копируем. Месячный ULP автопролонг не включает.
  • Тариф группы: если в M у группы есть шаблон, а в M+1 пакета нет — пишем тот же шаблон и текущую каталожную цену. Иначе группу пропускаем, учеников разбираем отдельно.
  • Пропуск с отчётом (не ошибка): в M+1 уже другой пакет/сумма; M+1 оплачен; ULP разложен; classic-автопролонг (UserLessonPackageAutoProlongGuard); шаблон недоступен; тип без права (type_denied / postpay_denied). Совпадающие пакет и пересчитанная сумма — идемпотентный no-op. В skip_reasons ученики и группы считаются раздельно (students / teams), без суммы в одном числе. У счётчика «Пропущено» иконка i из @include('partials.ui.tooltip-hint') (клон #setting-prices-prolong-skip-hint-tpl): в UI только ученики, ховер с причинами. Пустой источник — «В сентябре не установлены абонементы» (месяц M в предложном падеже). Плашку summaryMessage («Будет пролонгировано…») модалка не показывает (текст остаётся в JSON/toast).
  • Оплата, ручная отметка, ссылки СБП с M не копируются. Новый месяц неоплаченный.
  • Превью всегда JSON. Apply: AJAX JSON / non-AJAX 302. Ошибка месяца — 422 на selectedDate. Строка с ошибкой sync не валит весь прогон.
  • Модалка стандартной ширины Bootstrap, стилистика журнала (cell-edit-modal / cell-edit-context, resources/css/schedule.css). После успеха — Modal.hide и toast, без обновления тела модалки. Аудит pricing.month_prolonged (legacy action 15). Право — setPrices.view.
  • Кабинет ячейку M+1 покажет с 1-го числа M+1; письма уведомлений — по уже настроенным правилам (начисление в середине M может попасть в рассылку раньше).

Сервис: App\Services\SettingPrices\MonthlyPricesProlongService. Request: ProlongMonthlyPricesRequest. JS: Vite-модуль resources/js/settings-prices.js (initMonthProlong, после npm run build).
