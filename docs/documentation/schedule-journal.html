Журнал расписания: /schedule

Файл: /docs/documentation/schedule-journal.html · вкладка «Журнал»: GET /schedule (schedule.index) · см. также Нагрузка тренеров, Календарь школы
Единый контур с календарём школы (2026‑07). Журнал /schedule — дневное представление тех же занятий (user_team_schedule_slots + актуальный статус из user_lesson_occurrence_status_events). Календарь школы — то же + время слота. Таблица schedule_users и модель ScheduleUser удалены; «Личное расписание» и mass-range API сняты. Смена статуса в журнале списывает/возвращает lessons_remaining через UserLessonOccurrenceStatusService (тот же сервис, что в календаре). Справочник статусов общий: lesson_occurrence_statuses (вкладка «Статусы занятий», см. §8).
Пункт меню «Журнал расписания» — resources/views/includes/sidebar.blade.php (@can('schedule.view') или schedule.trainerSalary.view; ссылка на /schedule или /schedule/trainer-salary).
Маршруты вкладки «Журнал» / «Нагрузка» — middleware('can:schedule.view'). Вкладка и CRUD «Статусы занятий» — Gate lessonOccurrenceStatuses.manage (= schedule.view OR lessonPackages.view), см. §8. Вкладки «ЗП тренеров» / «Листы ЗП» — schedule.trainerSalary.*.

В config/role_base_permissions.php для роли admin строка schedule.view по умолчанию закомментирована — на новом партнёре право нужно включить в матрице прав.

2.1) Список строк в журнале: только активные ученики

В таблице вкладки «Журнал» и во всех user-эндпоинтах журнала (cell-context, update, abonement-context, place-fixed, sync-teams) участвуют только пользователи, которые одновременно:
  • принадлежат current_partner;
  • имеют users.is_enabled = 1;
  • имеют системную роль user (roles.name = 'user' и roles.is_sistem = 1, сидер RolesSeeder, id=3).

Кого нет в списке

Тип пользователяПочему не отображается
Администратор (roles.name = admin)Не ученик; системная роль admin
Тренер (roles.name = trainer)Не ученик; учёт тренеров — через trainer_profiles и вкладки «Нагрузка» / «ЗП» (см. Тренеры)
Пользователь с кастомной ролью партнёра (roles.is_sistem = 0)Даже если в UI роль называется «ученик» или «VIP» — в журнал не попадает. Кастомные роли: settings-roles-custom
Отключённый ученик (is_enabled = 0)Фильтр активности
СуперадминДругая системная роль
Согласованность с /admin/users: и журнал, и вкладка «Пользователи» в админке показывают только учеников (системная роль user). Отличие журнала — дополнительно is_enabled = 1 и контекст посещаемости; тренеры, администраторы и кастомные роли — на других вкладках раздела (см. admin-users-section).

Реализация

  • Scope модели User::scopeWithSystemRoleUser() — whereHas('role') с name = user и is_sistem = true.
  • ScheduleController::index() — partner_id + is_enabled = 1 + withSystemRoleUser(); затем фильтры год / месяц / группа (all / none / id) — по pivot team_user (User::filterByStudentTeam).
  • API: findScheduleStudentForPartner() и assertScheduleStudent() — те же условия; иначе 404.

Строки user_team_schedule_slots / события статусов для пользователей, которые больше не проходят фильтр (смена роли, отключение), в БД могут остаться, но строка в таблице журнала не выводится и изменить ячейку через API нельзя. Отчёт «Нагрузка тренеров» агрегирует актуальные события «Посетил» с trainer_profile_id по включённым пользователям партнёра (is_enabled = 1) без проверки роли ученика.

3) Данные: единый контур занятий

3.1) user_team_schedule_slots (занятие ученика)

Источник истины для журнала и календаря школы. Одна строка = одно занятие ученика (дата в starts_at, слот группы team_schedule_slot_id, опционально назначение user_lesson_package_id).

Поле / связьОписание
user_idУченик партнёра (круг §2.1 для UI/API журнала)
team_schedule_slot_idСлот группы (team_schedule_slots: weekday + время)
starts_atДата занятия в календаре/журнале (ключ дня)
user_lesson_package_idНазначение абонемента или NULL (пробное / без абонемента)
is_trial_lessonПробное занятие (баланс trial_lessons_*)

Модель: App\Models\UserTeamScheduleSlot. Сбор ячеек месяца: ScheduleJournalMonthService.

3.2) user_lesson_occurrence_status_events (статус занятия)

История статусов по занятию. Актуальный статус = последнее событие по ключу (ученик / слот / дата / ulp). На событии хранятся:

  • lesson_occurrence_status_id — FK на справочник;
  • trainer_profile_id — тренер при «Посетил» (nullable);
  • comment — комментарий к статусу (nullable).

Смена статуса идёт через UserLessonOccurrenceStatusService::apply: при consumes_lesson списывает/возвращает lessons_remaining (или пробный баланс). Журнал и календарь школы используют один сервис.

3.3) lesson_occurrence_statuses (единый справочник)

Один справочник на партнёра для журнала (/schedule) и календаря школы (абонементы). Таблица statuses и модалка «Настройки статусов» на журнале удалены.
Типpartner_idis_systemПримеры (code)Кто создаёт
Системные id партнёра (не глобальные) true «Посетил» (attended), «Не посетил» (not_attended), «Запись» (scheduled), «Отмена», «Заморозка» LessonOccurrenceStatusesSeeder::ensureForPartner при создании партнёра и при открытии UI
Кастомные id партнёра false произвольное название, code = custom_… Админ во вкладке «Статусы занятий» (оба экрана)
  • Поля: title, color, icon, sort_order, is_active, consumes_lesson.
  • В селекте ячейки журнала — только is_active = true. Неактивный статус на уже сохранённом занятии всё ещё отображается (lookup по полной выборке партнёра).
  • «Посетил» для тренера / нагрузки: LessonOccurrenceStatus::attendedIdForPartner($partnerId) (code = attended).
  • Флаг consumes_lesson применяется и в журнале, и в календаре — через UserLessonOccurrenceStatusService.
  • Занятие без события статуса (например, только привязка из календаря) в журнале всё равно видно: серая точка fa-circle.

6) Статус занятия и тренер при «Посетил»

Назначение тренера — только в модалке ячейки. Данные использует отчёт «Нагрузка тренеров» (фильтр по актуальному событию «Посетил» с непустым trainer_profile_id).

6.1) Поведение в модалке

  1. При открытии — GET /schedule/cell-context?user_id=&date=&utss_id= (опционально).
  2. Блок «Тренер» показывается, если выбран статус с code = attended (id из visited_status_id).
  3. В select — активные тренеры партнёра + «Без тренера».
  4. Если «Посетил» ещё не сохранялся — дефолт = первый тренер группы (team_trainer по context_team_id / слоту).
  5. Если «Посетил» сохранён с trainer_profile_id = null — явное «Без тренера».
  6. Смена статуса с «Посетил» на другой — тренер на новом событии не сохраняется как «посетивший» (логика сервиса статусов / UI).

6.2) API GET /schedule/cell-context

Валидация: GetScheduleCellContextRequest. Ученик — круг §2.1, иначе 404.

  • visited_status_id — id attended текущего партнёра
  • occurrences[] — занятия дня (UTSS + актуальный статус; у postpay — is_postpay, без времени слота)
  • postpay_teams, postpay_team_id — группы с постоплатой на дату (для модалки create)
  • selected / current_status_id / comment — выбранное занятие
  • team_ids, teams_label, team_default_trainer_profile_id, trainer_profile_id_for_select, trainers

6.3) API POST /schedule/update

Валидация: UpdateScheduleJournalOccurrenceRequest — поля user_id, utss_id, occurrence_date, lesson_occurrence_status_id, опционально trainer_profile_id, comment.

  • Пишет событие статуса через UserLessonOccurrenceStatusService (списание/возврат остатка по consumes_lesson)
  • trainer_profile_id / comment сохраняются на событии
  • AJAX / JSON → { success, message } 200; валидация → 422 + errors
  • Non-AJAX (нет XHR / не expectsJson) → 302 на schedule.index + flash status / session errors (не пустой 200)

Аудит: событие категории schedule (смена статуса дня / занятия).

После успешного AJAX UI делает window.location.reload() (schedule.js).

6.4) Связь с тренерами и группами

Дефолтный тренер = первый в team_trainer для контекстной группы слота — привязка тренера к группе. M:N групп: student-team-membership.

7) Раскладка фиксированного абонемента из журнала

v1: из журнала раскладывается только fixed. Flexible / no_schedule — через календарь школы. Логика: JournalFixedAbonementPlacementService + JournalTeamScheduleSlotEnsureService (время слота для дневного UI).

7.1) UI

  1. Кнопка «Абонемент» в строке ученика → GET …/abonement-context.
  2. Модалка #abonementPlaceModal: выбор назначения (только placeable), группа, дата начала, дни недели, превью, «Разложить».
  3. Кнопка disabled, если у назначения уже есть период (starts_at/ends_at) или строки UTSS (placeable = false).

7.2) Правила раскладки

  • Шаблон назначения — lesson_packages.schedule_type = fixed, назначение без периода и без UTSS.
  • Вход: user_lesson_package_id, team_id, start_date, weekdays[] (ISO 1…7), опционально preview.
  • Для каждого выбранного weekday берётся самый ранний enabled team_schedule_slot группы; если нет — создаётся служебный слот 09:00–10:00 (далее 10:00–11:00 … при коллизии).
  • Строится цепочка длиной до lessons_total (как assign-fixed календаря); задаётся период назначения; создаются UTSS.
  • На каждое занятие пишется статус «Запись» (scheduled) через тот же status-service.
  • preview=true — считает даты/кол-во, не пишет в БД.
  • Повторная раскладка того же назначения → 422 (поле user_lesson_package_id).

7.3) Контракт ответов

ЗапросУспехОшибка

То же safety-net (302 + запись) для schedule.update и user.sync.teams.

8.4) Safety-net: non-AJAX

Без Accept: application/json / без ожидания JSON (!$request->expectsJson()):

  • store / update / destroy — запись создаётся/обновляется/удаляется, ответ 302 на admin.lesson-packages.occurrence-statuses.index (не пустой 200);
  • ошибка валидации FormRequest — 302 back + session errors;
  • POST …/columns-settings без AJAX-заголовков — по-прежнему JSON { success: true } (как у других справочников); невалидный payload → 422 / 302, не пустой 200.

  • lesson_occurrence_status.created — снимок полей статуса.
