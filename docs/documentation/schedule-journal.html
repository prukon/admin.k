2.1) Список строк в журнале: только активные ученики

В таблице вкладки «Журнал» и во всех user-эндпоинтах журнала (cell-context, update, abonement-context, place-fixed, place-flexible, empty-cell-*, sync-teams) участвуют только пользователи, которые одновременно:
  • принадлежат current_partner;
  • имеют users.is_enabled = 1;
  • имеют системную роль user (roles.name = 'user' и roles.is_sistem = 1, сидер RolesSeeder, id=3).

Кого нет в списке

Тип пользователяПочему не отображается

Тренер (roles.name = trainer)Не ученик; учёт тренеров — через trainer_profiles и вкладки «Нагрузка» / «ЗП» (см. Тренеры)

Согласованность с /admin/users: и журнал, и вкладка «Клиенты» в админке показывают только учеников (системная роль user). Отличие журнала — дополнительно is_enabled = 1 и контекст посещаемости; тренеры, администраторы и кастомные роли — на других вкладках раздела (см. admin-users-section).

Реализация

  • Scope модели User::scopeWithSystemRoleUser() — whereHas('role') с name = user и is_sistem = true.
  • ScheduleController::index() — partner_id + is_enabled = 1 + withSystemRoleUser(); затем фильтры год / месяц / группа (all / none / id) и поиск q — по pivot team_user (User::filterByStudentTeam) и ФИО. Список учеников пагинируется, занятия и абонементы грузятся только для текущей страницы — см. §2.2.
  • API: findScheduleStudentForPartner() и assertScheduleStudent() — те же условия; иначе 404.

Строки user_team_schedule_slots / события статусов для пользователей, которые больше не проходят фильтр (смена роли, отключение), в БД могут остаться, но строка в таблице журнала не выводится и изменить ячейку через API нельзя. Отчёт «Нагрузка тренеров» агрегирует актуальные события «Посетил» по pivot user_lesson_occurrence_status_event_trainers по включённым пользователям партнёра (is_enabled = 1) без проверки роли ученика.

2.2) Пагинация списка и поиск q

Без пагинации таблица журнала рендерит всех учеников × дни месяца и упирается в memory limit (OOM на GET /schedule при ~1000 учениках). Список режется на сервере: ScheduleController::JOURNAL_STUDENTS_PER_PAGE = 100. Занятия, fixed/flexible ULP и галочка оплаты месяца грузятся только для id текущей страницы (fixedAssignmentsByUser(), не N+1 fixedAssignmentsForUser()).

ПравилоПоведение
Больше 100 учеников в выборкеПейджер .schedule-journal-pagination («Показаны N–M из K учеников» + Laravel links). Номера строк — $users->firstItem() + $index (на стр. 2 первая строка = 101).
100 и меньшеПейджера нет: не навязываем блок «из N учеников» и не рисуем page=2.
ПоискGET-форма «Найти» и Enter в поле q — серверный поиск по всей выборке (фамилия / имя / склейка ФИО; max 191, trim). Скрытые year / month / team (и fullscreen=1, если уже в URL). Нет hidden page: поиск со 2-й страницы открывает 1-ю страницу совпадений. Автопоиска при вводе нет. DataTables (paging: false) — только сортировка колонок на текущей странице.
Смена года / месяца / группыПолный GET (window.location.href). Обе копии JS (resources/js/schedule.js и hotfix public/js/schedule-journal.js) делают searchParams.delete('page') после set('team') и не удаляют q.
ВалидацияGetScheduleJournalIndexRequest: HTML GET → 302 + session errors[field] под фильтром; JSON (Accept: application/json) → 422 errors.year|month|team|q|page. Пустой team → all. POST/PATCH/DELETE /schedule → 405, не 500.

Изоляция партнёра та же, что в §2.1. Без current_partner — logout и ошибка под Email «Ваша организация недоступна.». Тесты: ScheduleJournalPaginationFeatureTest (HTTP 200/403/401/302/405/422, UX-баг «все ученики на стр. 1», форма поиска без page, пейджер только при >100, пакетная загрузка ULP), ScheduleJournalSearchFeatureTest, ScheduleJournalSearchAccessFeatureTest, BladeInlineJsSyntaxTest::test_schedule_journal_pagination_and_search_js_contract (node --check обеих копий JS + контракт: нет keyup/автопоиска, сброс page при смене фильтра).

3) Данные: единый контур занятий

3.1) user_team_schedule_slots (занятие ученика)

Источник истины для журнала и календаря школы. Одна строка = одно занятие ученика (дата в starts_at, слот группы team_schedule_slot_id, опционально назначение user_lesson_package_id).

Поле / связьОписание
user_idУченик партнёра (круг §2.1 для UI/API журнала)
team_schedule_slot_idСлот группы (team_schedule_slots: weekday + время)
starts_atДата занятия в календаре/журнале (ключ дня)
user_lesson_package_idНазначение абонемента или NULL (пробное / без абонемента)
is_trial_lessonПробное занятие (баланс trial_lessons_*)

Модель: App\Models\UserTeamScheduleSlot. Сбор ячеек месяца: ScheduleJournalMonthService.

3.2) user_lesson_occurrence_status_events (статус занятия)

История статусов по занятию. Актуальный статус = последнее событие по ключу (ученик / слот / дата / ulp). На событии хранятся:

  • lesson_occurrence_status_id — FK на справочник;
  • trainer_profile_id — primary/legacy тренер при «Посетил» (первый из списка, nullable);
  • pivot user_lesson_occurrence_status_event_trainers — все тренеры визита (каждому идёт зачёт в нагрузке/ЗП);
  • comment — комментарий к статусу (nullable).

В модалках «Статус занятия» и «Занятие из гибкого абонемента» при «Посетил» — мультиселект trainer_profile_ids[] (KidsCrmGenericMultiselectSelect2); пустой выбор = «Без тренера». В тултипе ячейки имена через запятую: Тренер: А, Б.

Смена статуса идёт через UserLessonOccurrenceStatusService::apply: при consumes_lesson списывает/возвращает lessons_remaining (или пробный баланс). Журнал и календарь школы используют один сервис.

3.3) lesson_occurrence_statuses (единый справочник)

Один справочник на партнёра для журнала (/schedule) и календаря школы (абонементы). Таблица statuses и модалка «Настройки статусов» на журнале удалены.

  • Поля: title, color, icon, sort_order, is_active, consumes_lesson.
  • В селекте ячейки журнала — только is_active = true. Неактивный статус на уже сохранённом занятии всё ещё отображается (lookup по полной выборке партнёра).

Это критично для партнёров без UI «Расписание школы» (только цены + журнал): школьные слоты с будущим date_start не должны ломать раскладку.
  • Строится цепочка длиной до lessons_total (как assign-fixed календаря); задаётся/дополняется период назначения; создаются UTSS.
  • На каждое занятие пишется статус «Запись» (scheduled) через тот же status-service.
  • preview=true — считает даты/кол-во и не пишет UTSS / не меняет период ULP; слот группы при необходимости всё же резолвится через ensure (может создать служебный team_schedule_slot, без записей ученика).
  • Повторная раскладка того же назначения → 422 (поле user_lesson_package_id).
  • AJAX place → 200 { success, message, … } / 422 с errors; non-AJAX POST → 302 на журнал + flash / session errors (не пустой 200) — запись при успехе создаётся.
Постоплата: раскладка fixed из журнала к postpay не относится. Postpay — отдельный контур (create_postpay в ячейке), ULP не создаётся — postpay.

Только ячейки без занятий (data-occurrence-count="0").
