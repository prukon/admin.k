1) Назначение и доступ

Раздел для работы школы с PDF-договорами учеников: список, создание, карточка, отправка на подпись (Подпислон / SMS), email, скачивание файлов.
Все маршруты обёрнуты в middleware('can:contracts.view') (routes/web.php). Без права — 403 (HTML и JSON).
Маршруты с {contract} дополнительно проверяют contract.partner (договор того же партнёра, что current_partner).
Синхронизация статуса с Подпислоном: GET …/status — отдельно can:contracts.sync. При первом переходе в signed (этот sync или вебхук Подпислона) админы школы получают in-app уведомление на 7 суток (анонс, §8.1). Право groups.own сужает селект групп в модалке создания (restrictTeamsQuery), список договоров без фильтра группы не режется. Подробно — groups-own, анонс /doc.

1.3) Колонка «Обновлён» в списке

Заголовок колонки — «Обновлён» (<th>, чекбокс #colUpdatedAt, ключ настроек updated_at). Значение в GET /client-contracts/data — не contracts.updated_at, а created_at последнего события журнала этого договора: contract_events с тем же contract_id, строка с максимальным id (как аккордеон «Журнал событий» на карточке: $contract->events()->orderBy('id', 'desc')), формат d.m.Y H:i:s. Автор события не фильтруется.

Штатное создание через UI всегда пишет событие created («Создан») в ContractCreationService. Без строк в contract_events — пустая ячейка. Сортировка колонки (индекс 9 DataTables) — по этой дате, без событий в конце. Дефолт списка — индекс 1 («Номер договора»), не эта колонка. Timeline «(посмотреть)» эту колонку не использует. Анонс: /doc.

1.4) Колонка «Срок подписания» в списке

Заголовок колонки — «Срок подписания» (<th>, чекбокс #colFillExpiresAt, ключ настроек data-column-key="fill_expires_at"). Колонка и пункт в меню «Колонки» рендерятся только при скрытом праве contracts.fillExpiresAt.view (is_visible=0, не в role_base_permissions, миграция 2026_09_12_062900_add_contracts_fill_expires_at_view_permission ролям не выдаёт). Superadmin видит колонку через Gate::before. В матрице «Права и роли» чекбокс права видит только superadmin. DataTables: when: canSeeFillExpiresAt, дефолт сортировки списка — индекс 1 («Номер договора», анонс). С правом колонка стоит после «Обновлён» (индекс 10), сортировка по contracts.fill_expires_at, пустые в конце.

Значение в GET /client-contracts/data — contracts.fill_expires_at в формате d.m.Y H:i:s (дата и время дедлайна заполнения/подписания, при создании по шаблону now() + FILL_TTL_DAYS). Без срока — пустая ячейка. Вторая строка той же ячейки — короткий остаток календарных дней: «N день/дня/дней», сегодня — «Последний день» (CLIENT_FILL_REMAINING_LAST_DAY), просрочка — «Срок истек.» (SCHOOL_LIST_FILL_REMAINING_EXPIRED) (schoolListFillRemainingDaysLabel(); JSON fill_expires_remaining / fill_expires_remaining_warn). У signed и без срока второй строки нет. Меньше 6 дней и «Срок истек.» — text-danger. Без права ключей fill_expires_at, fill_expires_remaining и fill_expires_remaining_warn в JSON нет. Это не строка «Срок заполнения» на карточке договора (§2.1: template + непустой срок, формат d.m.Y H:i, достаточно contracts.view) и не подпись ЛК «Осталось N дней» (анонс ЛК). Анонс колонки: /doc; остаток дней и номер: /doc.

1.5) Колонка «Номер договора» в списке

3.1) Подпислон

Провайдер: App\Services\Signatures\Providers\PodpislonProvider. API-ключ берётся с юр. лица договора (partner_legal_entities.podpislon_api_key через PodpislonCredentialsResolver), не из PODPISLON_API_KEY (анонс). Резолюция юр. лица — LegalEntityResolver::forTeamId(group_id, school_id); при 2+ юр. лицах без явной привязки группы отправка блокируется (422). Без ключа — 422, статус договора не меняется на failed. После первой отправки пишется contracts.legal_entity_id.
HTTP 200 с JSON status: false — отказ, не успех: событие sent не пишется, UUID в provider_request_id не подставляется, текст message уходит в UI (§3.1.2, анонс).
В PUT /add-document передаются name (имя), last_name (фамилия), second_name (отчество), phone — из данных формы отправки (оператор может изменить перед SMS), не напрямую из БД после отправки.
После отправки в contract_sign_requests фиксируется снимок подписанта; сменить подписанта у уже созданного договора нельзя — только новый договор или новая отправка с новыми данными в форме.
Вебхук: POST /webhooks/podpislon (имя webhooks.podpislon), без CSRF, без самодельного ?token=. В кабинете Подпислона у каждой компании — этот URL как есть. Пустой POST (проверка URL) — 200 probe. События — поле SIGNATURE Подпислона (md5 тела без SIGNATURE). Кастомный query-токен не проверяется и не заменяет SIGNATURE. Гость и сотрудник без contracts.view получают тот же 200 на пробу (не логин и не 403). CSRF не требуется. GET/PUT/PATCH/DELETE — 404/405, не 500. Path /webhooks/podpislon/{token} не существует (404/405, не 200).

3.1.1) Ссылка на подпись из SMS

Анонс: /doc. В OpenAPI Подпислона у контакта поле contacts[].link (пример https://podpislon.ru/sign/pack/861221/58abc612882) — та же ссылка, что в SMS. SMS по-прежнему шлёт Подпислон: параметр no_sms при PUT /add-document не передаём.
Колонка contracts.provider_signing_url (nullable string). Пишет PodpislonSigningUrl::capture() только URL вида https://podpislon.ru/sign/pack/{digits}/{hex}: после первой отправки (ContractPodpislonSendService / ответ /add-document), при ресенде и при GET /client-contracts/{id}/status — даже если статус уже sent (synced: false). Чужой хост не сохраняется. Вебхук ссылку не присылает и колонку не трогает — для старых договоров достаточно «Синхронизировать с Подпислон». Отзыв / аннулирование колонку не очищают: строка на карточке остаётся, пока URL проходит whitelist. Список /client-contracts ссылку не показывает (нет поля в data). Карточка: строка не за @can('contracts.sync') (#contract-provider-signing-url). Обе кнопки SMS открывают #sendModal; #sendSubmit всегда POST /client-contracts/{id}/send (даже повторно). Успех: showSuccessModal(..., 1) — reload после OK, чтобы появилась ссылка. Sync — location.reload(). Native POST /send без X-Requested-With тоже пишет URL (JSON 200). 422: errors.signer_lastname / errors.signer_phone / errors.podpislon_api_key — URL не пишется. Карточка CRM — §2.1. Кабинет родителя — кнопка «Открыть ссылку из SMS» (account-contract-fill); повтор SMS без смены номера — §1.5, анонс.

3.1.2) Текст ошибки Подпислона в CRM

Анонс: /doc. PUT /add-document может вернуть HTTP 200 и JSON {"status":false,"message":"Не выбран провайдер отправки смс."}. Это отказ: документ не создан, SMS не ушла. PodpislonProvider::send() не пишет sent, не ставит UUID в provider_request_id, после status: false не делает JSON-fallback. ContractPodpislonSendService ставит договор в failed, событие failed с payload_json.message и сырым res, JSON 422 message + code: send_not_sent. pollForSent без provider_doc_id сразу null (без паузы 3×300 мс).

Карточка: #contract-status-error только при текущем failed и непустом Contract::lastFailureMessage() (последнее событие failed/resend_failed); при sent старое failed-событие в журнале остаётся, под бейджем строки нет. Журнал: .contract-event-error, если userFacingMessage() не пустой (в том числе старый payload без ключа message: res.raw.message / error); у типичного sent текста нет — блока нет. Список: JSON status_error (null, если не failed или текста нет), бейдж с title только если текст есть, без новой колонки. Модалка: и «Отправить СМС», и «Повторно отправить» открывают один #sendModal и POST /send (не /resend); onSendFailure пишет json.message в #error-modal-message. Native POST /send без X-Requested-With тоже JSON 422 (не 302 на список). Нет message в ответе Подпислона — generic «Провайдер не подтвердил отправку SMS.» Кабинет родителя #contract-status-error не рисует; account.documents.sign при отказе — 302 с errors.sign, не JSON 422 CRM (account-contract-fill).

4) Скачивание PDF в интерфейсе

Три места, критерии разные. Не смешивать список, карточку CRM и кабинет.
  • Карточка CRM /client-contracts/{id}, блок «Файлы»: критерий кнопок — поле contracts.status. Статус signed (Contract::STATUS_SIGNED) — только «Скачать подписанный» (route('contracts.downloadSigned')), даже если путь пуст (тогда 302 errors.file). Любой другой статус — «Скачать оригинал» (source_pdf_path); если уже есть signed_pdf_path (клиент подписал старое SMS после аннулирования) — показываются оба файла.
  • Кабинет «Мои документы»: «Скачать подписанный» — если заполнен signed_pdf_path (любой статус, в т.ч. revoked). «Скачать PDF» оригинала — если статус не signed и есть source_pdf_path.
  • Список CRM /client-contracts: иконка PDF — только filled(signed_pdf_path), статус не смотрит (§4.1.1). Это не колонка «Договор» на /admin/users (там PDF открывает карточку при signed).
  • Файлы: диск local, storage/app/ + относительный путь из БД.

5.3) Предзаполнение и открытие модалки

  • ?create=1, ?user_id={id} или ошибки валидации после POST — флаг shouldOpenCreateModal, модалка открывается при загрузке страницы.
  • Валидный user_id своего партнёра (is_enabled = 1) → preselectedUser: id, text, team_ids, team_id (первая группа), team_title, groups[], parent_full_name (или null).
  • Чужой партнёр / несуществующий id — preselectedUser = null, модалка всё равно может открыться по query.
  • Переход из заявок (прямая ссылка): GET /client-contracts?user_id=… или legacy GET /client-contracts/create?user_id=… → redirect на index с теми же параметрами. Основной UX на странице заявок — встроенная модалка без смены страницы (§school-leads-widget §5.8).
  • JS API: window.KidsCrmContractCreate.openModal(preselectedUser, options?) — используется на /admin/school-leads, /admin/users и на /client-contracts. Опция { lockUser: true } (клик по строке клиента/лида): ученик предзаполнен, Select2 задисейблен, без очистки; в форму уходит hidden #user_id_locked. Без опции (кнопка «Создать» на списке договоров, query ?user_id=) поле остаётся редактируемым.

5.4) Сохранение и оплата

  • Footer модалки: «Отмена» и «Создать договор» (#btn-save).

  • Списание с баланса партнёра — только при успешном POST /client-contracts, не при открытии модалки.
  • После создания ученика и группы изменить нельзя — только новый договор.
  • Текст подтверждения (showConfirmDeleteModal в onSaveClick): pdf — «Изменить файл и ученика после создания договора будет нельзя. Стоимость создания договора 70 руб. 7) Режим «форма клиенту» (creation_mode=template)

В модалке «Создать договор» (§5) переключатель «Способ создания»: pdf — загрузка готового PDF (классический сценарий CRM); template — выбор шаблона DOCX, договор уходит клиенту на заполнение в кабинете.

При успешном POST /client-contracts с template: списание 70 ₽, статус awaiting_client_fill, fill_expires_at +30 дней (Contract::FILL_TTL_DAYS), redirect на GET /client-contracts/{id} (карточка), не на index. Flash: «Договор создан. С баланса списано 70 ₽. Клиенту отправлено уведомление в личный кабинет (и на email, если указан).»

Списание идёт через ContractBillingService: partners.wallet_balance_cents минус 70 ₽ и debit в partner_wallet_transactions («Создание договора», meta.reason=contract_create). Отзыв awaiting_client_fill возвращает 70 ₽ на баланс и пишет credit «Возврат: отзыв договора» (provider=refund); исходный debit остаётся succeeded.

Ученик чужого партнёра → 422 (ContractCreationService). Недостаточный баланс → redirect на index с ?create=1, ошибка в wallet (ValidationException).

7.2) Аннулирование sent/opened (без возврата 70 ₽)

Анонс: /doc. Один endpoint POST /client-contracts/{contract}/revoke (ContractSigningController::revoke, право contracts.view): awaiting_client_fill → отзыв с возвратом; sent/opened → annulAfterSend; иначе вызов provider->revoke() (Подпислон бросает → JSON 422, статус не меняется).
ЧтоФакт в коде
Когда можно Contract::canAnnulAfterSend() — статус sent или opened (режим PDF и template одинаково). Кнопка #annulAfterSendBtn «Аннулировать». draft / generating_pdf / signed / failed / expired / revoked — кнопки нет; POST → 422 + message.
Чего нет Возврата 70 ₽ и credit в partner_wallet_transactions. Вызова API Подпислона. Колокольчика при поздней подписи старого SMS. Очистки provider_signing_url (строка «Ссылка на подпись» и кнопка в кабинете остаются, если URL валиден — §3.1.1).
JSON 200 message: «Договор аннулирован. 70 ₽ не возвращаются.»; status: revoked. Native POST без X-Requested-With тоже меняет строку (не пустой 200).
Аудит / событие contract.revoked; payload refunded: false, reason: annul_after_send; my_logs: «Договор аннулирован. Возврат 70 ₽: Нет». Бейдж статуса — «Отозвано» (Contract::$STATUS_RU).
JS на карточке Один обработчик #annulAfterSendBtn → confirm (текст про кабинет, 70 ₽, живое SMS, статус «Отозвано») → POST revoke → alert message → location.reload(). После аннулирования нет resend; sync только если revoked и нет signed_pdf_path (нужно contracts.sync).
Поздняя подпись Вебхук SIGNED / GET …/status: signed_at при пустом, докачка PDF, событие signed_after_revoke, статус остаётся revoked, $becameSigned нет. OPENED revoked не меняет. Файлы: оригинал + подписанный, если путь есть. Кабинет: нет fill/sign/edit; «Скачать подписанный» по signed_pdf_path.
/admin/users, заявки LatestUserContractLookup пропускает revoked. После аннулирования opened снова «Создать договор», если нет другого не-отозванного. Фильтр with считает любой договор, в том числе только revoked; unsigned — по последнему не-отозванному.
