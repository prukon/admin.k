Родители и семейный кабинет

Файл: /docs/documentation/parents-and-family-cabinet.html · URL: /docs/documentation/parents-and-family-cabinet · оглавление: /doc
Назначение. Справочник родителей (parents) для ФИО подписанта договора и семейного кабинета (несколько детей с одним users.parent_id). Вход в CRM — только под учёткой ученика (users, роль user). Отдельной учётки «мама/папа» нет. Контакты для SMS и оплат — users.phone / users.email учётки ученика, под которой выполнен вход. Карточка parents (ФИО, ФИО в родительном падеже, паспорт, адрес, телефон, email родителя) общая для всех детей с тем же parent_id и редактируется из админки (§3) и из ЛК (§4) при наличии права. При заявке с лендинга карточка может быть автоматически подобрана к лиду (school_leads.parent_id) — см. school-leads-widget §5.5.5.
Не путать с ФИО ученика в родительном. Родительный падеж ученика хранится в users.full_name_genitive (HTTP full_name_genitive, DOCX {{child_full_name_genitive}}), право users.full_name_genitive — см. admin-users §2.1.7. Это поле карточки ребёнка, а не справочника parents.

0) Как это работает (сценарий)

Пример. Брат 1 и брат 2 — две записи users с одним parent_id (одна строка в parents). Вход под любым из них даёт доступ к данным обоих через переключатель «Просмотр данных ученика» в левом сайдбаре (layout admin2). При создании из лида / «Добавить» с welcome: логин (users.email = parent_email) выдаётся первому ребёнку; второму — users.email = null и письмо «входите как раньше» (FamilyStudentLoginResolver, см. admin-users §5.1).
  • Права (роли, permissions) остаются у залогиненного ученика; переключатель меняет только контекст просмотра (платежи, консоль и т.д.) — session active_student_user_id. Оплата месяца / доп. платежа / абонемента с витрины тоже идёт в этот контекст: начисление, запись платежа и строка «Плательщик» — выбранный ребёнок, право paying.classes — учётка входа.
  • Если у ученика нет parent_id или нет второго активного ребёнка с тем же parent_id — переключателя нет.
  • При семейном режиме (переключатель виден) в сайдбаре над селектом «Имя» и «Почта» показываются parents.full_name и parents.email (см. FamilyStudentContextService::sidebarPanelIdentity).
  • Редактирование карточки родителя (ФИО, паспорт, адрес, телефон, email) в личном кабинете или в админке меняет общую запись parents — изменения видны всем детям с этим parent_id.

1.5) ФИО в родительном падеже

Поле для договоров и текстов («от имени Иванова Ивана Ивановича»). Хранится одной строкой, без автосклонения и без отдельных колонок фамилии/имени/отчества в родительном.
СлойЗначение

Что это поле не делает. Не участвует в колонке «Родитель», поиске по ФИО, подписи Select2, выгрузке Excel календаря и read-only «ФИО родителя» в модалке создания договора — там именительный (ParentProfile::full_name / User::parent_full_name). В таблице school_leads отдельной колонки родительного нет: в модалке лида поле видно через _parent_form, но снимок заявки его не хранит; при выборе родителя из справочника значение подставляется из parents.
  • Валидация: nullable|string|max:300; ошибки — ключ parent_full_name_genitive (под полем).
  • Админка: ФИО именительные не обязательны вместе с родительным (можно сохранить только genitive в профиле при уже существующей карточке / вместе с другими parent_*).
  • ЛК: при любом заполненном поле блока родителя обязательны фамилия и имя — одно только genitive → 422.
  • Пустая строка при наличии ключа в запросе очищает full_name_genitive (в отличие от части других profile-полей с «только non-null fill»).

Тесты: AdminUsersParentFullNameGenitiveFeatureTest, AccountParentFullNameGenitiveFeatureTest, ContractParentFullNameGenitivePrefillFeatureTest, BladeInlineJsSyntaxTest::test_edit_user_and_parent_form_genitive_fill_contract_is_valid_javascript. 3) Админка: ученики (/admin/users)

Список и создание на этой странице — только роль user (ученик, вкладка «Клиенты»). Обзор вкладок раздела: admin-users-section. Нейминг — /doc.

Подробно: admin-users §2.1 · колонка телефона родителя: §2.1.0 · правка из справочника: §2.1.2 · родительный падеж: §2.1.6 / §1.5. Кратко:

МетодURLНазначение
GET/admin/users/parents/searchSelect2: поиск родителей текущего партнёра (q, id, limit)
POST / PATCH/admin/users, /admin/users/{user}parent_id и/или parent_* в теле → StudentParentSyncService::syncForStudent
Общая карточка. В режиме «Из справочника» ФИО, родительный падеж и поля профиля редактируемы. Сохранение с parent_id обновляет существующую parents — изменение видно всем детям с тем же parent_id (колонка «Родитель», «Телефон родителя», edit JSON, ЛК, договоры). «Новый родитель» создаёт новую строку.
  • В модалках create/edit: блок родителя только для роли user; переключатель «Из справочника» / «Новый родитель» (если в справочнике есть записи), иначе сразу поля ФИО — см. admin-users §2.1.2.
  • В списке DataTables: колонка «Родитель» — склейка ФИО из parents; колонка «Телефон родителя» (parent_phone) — parents.phone (пусто, если нет родителя/телефона); заголовок «Телефон ученика» — users.phone. Подробно — admin-users §2.1.0.
  • Поиск по name ищет по ФИО в parents и по parents.phone (а также по ФИО/email/телефону/ДР ученика).
  • Сортировка: col=3 — parents.lastname, parents.firstname; col=4 — parents.phone (left join; индексы при полном наборе колонок, см. admin-users §2).
  • Право: достаточно users.view + store/update пользователя; отдельного permission на родителя в админке нет.
  • HTTP: AJAX → JSON; non-AJAX POST/PATCH → redirect на список учеников (safety-net).
  • Пол и комментарий ученика — §admin-users §2.4: пол — users.sex (CRM и кабинет), комментарий — только CRM (users.comment, §4.4).

4.2) Сохранение

  • PATCH /account-settings/user — AccountUpdateRequest + AccountController@update.
  • Поля родителя валидируются и сохраняются только при роли user и праве account.user.parent.update.
  • Пол (sex) — только при users.sex (§4.4).
  • ФИО ученика в родительном (full_name_genitive) — только при users.full_name_genitive (admin-users §2.1.7); 422 → ключ full_name_genitive.
  • Сервис: StudentParentSyncService::updateFromAccount — обновляет parentProfile ученика; при отсутствии создаёт запись в parents и выставляет users.parent_id.
  • Правка ФИО/профиля в ЛК меняет общую карточку — sibling с тем же parent_id видит изменения сразу (без отдельной учётки родителя).
  • Ответ всегда JSON (success, message); ошибки валидации — 422, ключи parent_lastname, parent_full_name_genitive, full_name_genitive, sex и т.д. (вывод под полями на фронте).
  • ФИО родителя в родительном падеже: необязательное поле parent_full_name_genitive → parents.full_name_genitive (max 300). Пустая строка очищает значение. В ЛК одно только это поле без фамилии/имени → 422 на parent_lastname/parent_firstname.

4.3.1) Смена своего пароля

Кнопка «Изменить пароль» на /account-settings/user/edit открывает #change-pass-wrap (при первом открытии страницы скрыт, #error-message тоже скрыт; клик — display: inline-block). Анонс — /doc.

1) Успех. PUT JSON 200 {success: true}, toast «Пароль успешно изменен.» (window.showToast), не showSuccessModal. Блок снова скрыт, поле очищается.
2) Тот же пароль, что уже стоит (в том числе повтор сразу после успешной смены): JSON 422 errors.password «Новый пароль совпадает с текущим.», без записи в my_logs. UI — текст сервера в #error-message под полем, блок не закрывается, без toast и без showErrorModal. Короткий / пустой / длиннее 255 — 422 errors.password (на клиенте длина < 8 отсекается до запроса).
3) Не в этом контракте. Вкладка «Мои документы» (myDocuments.blade.php) этот UX пока не повторяет.

4.5) Группы ученика

На /account-settings/user/edit блок «Группы» — просмотр (readonly + disabled, значения из pivot $user->teams). Без права account.user.team.update — подпись «Изменение групп доступно только администратору CRM» (полный sync/замена/снятие — только CRM /admin/users, users.group.update). При праве — подпись скрыта; рядом с label — карандаш (includes/cabinet_attach_team_pencil.blade.php), если есть $cabinetTeamAttach (view composer на account.index); открывает ту же модалку attach, что сайдбар / /cabinet.
Добавление группы в ЛК. При праве account.user.team.update (is_visible=0, не в базовых ролях): сайдбар «Группа: … изменить», карандаш на /cabinet и на учётной записи, одна модалка attach. Кандидаты — только группы объектов текущих групп ученика; уже назначенные / disabled / soft-deleted не показываются. Действие — только attach. Endpoint: POST /cabinet/teams/attach (cabinet.teams.attach), AttachCabinetTeamRequest + CabinetTeamController + CabinetTeamAttachService → TeamUserSyncService::attachTeamForStudent. AJAX: ошибки — JSON errors.team_id (под select); успех — location.reload(). Non-AJAX safety-net: 302 back() + flash status. UI скрыт, если у активного ученика нет групп или у групп нет location_id. Семейный режим: attach — активный ребёнок из session; поле «Группы» на учётной записи — команды залогиненного профиля. После успешного attach админы и тренеры школы получают in-app уведомление (колокольчик, 30 суток; с родителем — «Родитель / Ребёнок / Добавлена группа», иначе «{ФИО} добавил группу») — анонс события, текст, in-app-notifications §5.1. См. dashboard-cabinet §7.1, анонс /doc, student-team-membership.

9) Что не поддерживается

  • Отдельная учётная запись родителя для входа (parents.user_id удалён).
  • Переключение между детьми при разных parent_id (разные записи в parents).
  • Переименование «только для одного ученика» без отвязки: правка ФИО / родительного всегда меняет общую карточку; для другой персоны — «Новый родитель» или смена parent_id.
  • Автосклонение ФИО и отдельные колонки фамилии/имени/отчества в родительном — только ручная строка parents.full_name_genitive (§1.5). Аналогично для ученика — users.full_name_genitive (admin-users §2.1.7), это не часть справочника parents.
  • Отдельный CRUD-раздел /admin/parents (карточка правится из модалки ученика / заявки / ЛК).
  • Семейный контекст на страницах договоров у роли user (договоры — право contracts.view, админка).
