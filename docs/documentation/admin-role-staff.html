Администраторы и сотрудники с кастомной ролью

Файл: /docs/documentation/admin-role-staff.html · URL: /docs/documentation/admin-role-staff · обзор вкладок: admin-users-section

1) Назначение и модель

Сотрудник (администратор или пользователь с кастомной ролью партнёра) — обычная запись users с фиксированным role_id. Отдельной таблицы профиля нет (в отличие от trainer_profiles у тренеров).
ФИО, email, телефон, пароль, аватар, активность — в users. При создании и обновении через эти страницы users.team_id сбрасывается в null.

2) Доступ

Все маршруты раздела в routes/web.php обёрнуты в middleware(['can:users.view', 'can:users.role.update']).
Без users.view или без users.role.update — 403.
Вкладка в разделе «Пользователи» видна только при users.role.update (см. admin-users-section).

Контроллер: App\Http\Controllers\Admin\RoleStaffUserController.
Запросы: StoreRoleStaffUserRequest, UpdateRoleStaffUserRequest (authorize: users.role.update).
View: resources/views/admin/role_staff/index.blade.php (общий шаблон для обеих страниц).

3) Администраторы — /admin/administrators

Системная роль roles.name = admin. Вкладка «Администраторы».

3.2) UI и колонки

  • Колонки: аватар, ФИО, email, телефон, активен, действия.
  • Фильтры: имя (ФИО / email / телефон), статус (active / inactive).
  • Создание — модалка: имя*, фамилия*, email, телефон, чекбокс «Отправить письмо» (§3.3), пароль (опционально; скрыт при включённом чекбоксе), активен. Успех: toast с message сервера (обычно «Пользователь создан»), не showSuccessModal.
  • Редактирование — аватар (editAvatar), смена пароля → POST /admin/user/{id}/update-password при users.password.update (§3.4). Повторной отправки пароля по email на этих страницах нет (только для учеников — admin-users §5.1.2).
  • Удаление — soft delete из модалки редактирования. Подтверждение через showConfirmDeleteModal (не window.confirm) → DELETE. Успех: edit-модалка закрывается (снятие hidden.bs.modal.return у confirm), AJAX reload таблицы, toast с message сервера (обычно «Пользователь удалён»), не showSuccessModal. Ошибка DELETE — showErrorModal.
  • Ошибки валидации — JSON 422, поля под формой.

3.3) Welcome-письмо при создании (send_welcome_email)

Общий механизм с учениками и тренерами (admin-users §5.1.4). Применяется и к POST /admin/administrators, и к POST /admin/roles/{name} (одна форма role_staff/index.blade.php).
  • UI: #role-staff-create-send-welcome-email, по умолчанию включён; пароль скрывается при checked.
  • При true: email обязателен; пароль генерируется; письмо синхронно.
  • AJAX 200: message, user, welcome_email_sent. SMTP fail → пользователь создан, флаг false.
  • Non-AJAX → redirect back() (обычно на index вкладки), запись создана.
  • Права: users.view + users.role.update.

3.4) Ручная смена пароля (модалка редактирования)

Кнопка «Сменить пароль» видна только при users.password.update ($canChangePassword). Без права блок в разметке не рендерится. При первом открытии карточки поле пароля скрыто (#role-staff-change-pass-wrap, display:none). Класса .change-pass-wrap у блока нет — style.display = '' здесь достаточно (в отличие от тренера, где тот же приём прячет форму из‑за CSS — admin-trainers §6.4).
  • Эндпоинт: POST /admin/user/{id}/update-password (admin.user.password.update), throttle 5/мин. Права: users.view + users.password.update.
  • AJAX 200: { "success": true }. Успех в UI: поле очищается, блок скрывается, всплывайка «Пароль успешно изменен» (window.showToast / #kidsMainToast в layout admin2).
  • Повтор того же пароля не уходит на сервер (клиент помнит последний успешный пароль по userId) — всплывайка «Новый пароль совпадает с текущим.» Без этого повторный клик «Сохранить пароль» давал 422 в консоли без понятного UI.
  • Если запрос всё же ушёл (другой клиент / тот же текущий пароль): JSON 422, message «Новый пароль совпадает с текущим.» (без errors.password). Слишком короткий / пустой: 422 errors.password.
  • Non-AJAX POST: успех — JSON 200 и запись обновлена (не пустой 200); валидация — 302 + session errors.password.
  • Гость — 302/401; без права — 403; чужой партнёр — 404. GET/PUT/PATCH/DELETE — 404/405, не 500.
Анонс: /doc §смена пароля.

4) Кастомные роли — /admin/roles/{name}

{name} — машинное имя роли (roles.name), только [a-z0-9_]+. Роль должна быть несистемной (is_sistem = 0) и привязана к текущему партнёру через partner_role. Подпись вкладки — roles.label из настроек роли.

6) Изоляция по партнёру

  • Список и операции — только users.partner_id = current_partner и ожидаемый role_id.
  • Чужой партнёр или пользователь другой роли на role-scoped маршруте → 404.
  • Кастомная роль другого партнёра → 404 на /admin/roles/{name}.
