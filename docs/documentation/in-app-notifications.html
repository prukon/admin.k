In-app уведомления CRM (колокольчик)

Файл: /docs/documentation/in-app-notifications.html · кабинет: /in-app-notifications · анонсы: автособытие attach, текст с родителем / без, колокольчик
Кратко. Лента сообщений внутри кабинета: колокольчик в шапке layouts.admin2 (перед «Выйти»), выпадашка из 3 последних, страница всех уведомлений. Ручную рассылку составляет только superadmin. Плюс автособытие: ученик добавил группу в ЛК → колокольчик admin/trainer школы (/doc, текст, §5.1). Ссылки живут внутри текста сообщения. Клик по пункту колокольчика открывает ленту и сразу помечает это уведомление прочитанным.
Не путать с вкладкой «Установка цен → Уведомления» (email по неоплаченным users_prices) и с чатом. Префикс в коде и БД: in_app_* / inAppNotifications.*.

1) Права

PermissionВидимость в матрицеБазовые ролиЧто даёт
inAppNotifications.view is_visible=1 user, admin, trainer Колокольчик, выпадашка, страница ленты, прочтение
inAppNotifications.manage is_visible=0 (в матрице видит только superadmin) не выдаётся Зарезервировано под форму админа школы. В v1 UI формы у админа школы нет

Группа матрицы: inAppNotifications («Уведомления CRM»). Форму создания в v1 открывает только superadmin (PartnerContext::isSuperAdmin), даже если кому-то выдадут manage — будет 403. Без view — 403 на все маршруты раздела; гость — редирект на логин.

2) Как это выглядит в кабинете

2.1 Колокольчик

  • Иконка в шапке admin2, справа, перед «Выйти». Есть на всех страницах этого layout (в том числе /cabinet).
  • Красный каунтер — точное число непрочитанных (не «9+»). Если непрочитанных нет — каунтер скрыт.
  • Выпадашка: заголовок «Уведомления», 3 самых новых (created_at DESC, id DESC), внизу «Показать все» → /in-app-notifications.
  • Превью текста — до 60 символов, экранированный текст без HTML (чтобы не вкладывать ссылки в пункт-<a>). Абзацы, <br> и пункты списка показываются переносами строк (white-space: pre-line на .bell-preview). Дата — по Москве, вид «13 августа 2026» (без времени).
  • Плашки «Важное» (бордо) и «Обновление» (голубой) — те же, что на странице ленты. Плашка «Обычное» не показывается.
  • Пункт выпадашки — ссылка на ленту /in-app-notifications?n={id}. Отдельного поля URL у уведомления нет: клик не уводит с сайта на внешний адрес.

2.2 Страница ленты /in-app-notifications

  • Тулбар в стиле кабинета: заголовок, счётчик непрочитанных, «Прочитать все» (если есть непрочитанные), «Создать» — только у superadmin.
  • Карточки: непрочитанные с жёлтой полоской слева. Фильтров нет. Пагинация по 20.
  • Простое открытие ленты не помечает все прочитанными. Помечается конкретное сообщение, если в URL есть ?n={id} (клик из колокольчика) или если нажали «Отметить прочитанным» / «Прочитать все».
  • При ?n={id} карточка подсвечивается и прокручивается в центр. Если id чужой или просроченный — страница 200, без подсветки и без записи о прочтении (не 500).
  • Пустая лента: «Пока тихо».

2.3 Ссылки в тексте

  • В форме создания отдельного поля «Ссылка» нет. Переход задаётся в тексте: выделить фрагмент → иконка цепочки в редакторе (Summernote: жирный, курсив, списки, ссылка).
  • Разрешены теги p, br, a, strong, b, em, i, u, ul, ol, li.
  • href: внутренний путь /... (не //) или http/https. Внутренняя ссылка открывается в той же вкладке CRM; внешняя — в новой (target=_blank, rel=noopener noreferrer).
  • javascript:, data:, <script> и прочий HTML отбрасываются и при сохранении, и при показе. Колонка action_url в таблице осталась, в v1 всегда null.

3) Маршруты

Группа auth + 2fa + can:inAppNotifications.view.

МетодURIИмяДоступ / ответ
GET/in-app-notificationsinAppNotifications.indexview, HTML ленты; ?n= помечает прочитанным
GET/in-app-notifications/bellinAppNotifications.bellview, JSON: unread_count + 3 items с page_url
POST/in-app-notifications/read-allinAppNotifications.readAllview; JSON при AJAX, иначе 302 на ленту
POST/in-app-notifications/{id}/readinAppNotifications.readview, только видимые; иначе 404. JSON или 302
GET/in-app-notifications/{id}/openinAppNotifications.openview: прочитать + редирект на ленту ?n={id}
GET/in-app-notifications/composeinAppNotifications.composeview + superadmin, иначе 403
GET/in-app-notifications/compose/rolesinAppNotifications.compose.rolessuperadmin, JSON ролей под выбранные школы
POST/in-app-notificationsinAppNotifications.storesuperadmin, обычная форма → 302 на ленту; JSON-валидация → 422 errors[field]

Форма создания — native POST (JS только синхронизирует Summernote и подгружает роли через fetch, без preventDefault на submit).

4) Рассылка (superadmin)

  1. Поля: заголовок, HTML-текст, тип (Обновление / Важное / Обычное), школы или «Все школы», роли, срок жизни.
  2. Дефолты первого открытия: тип «Обычное», срок «7 суток», «Все школы» выключено, блок школ виден, своя дата скрыта, пока не выбран TTL «Своя дата».
  3. При нескольких школах / «все школы» в ролях только системные user / admin / trainer. Кастомные роли (через partner_role) — только если выбрана одна школа. Смена школ в форме перезапрашивает список ролей и сохраняет уже выбранные id, если они ещё допустимы.
  4. Срок жизни: 1 / 7 / 30 суток, своя дата (конец дня Europe/Moscow), «пока не прочитают» (expires_at = null). Просроченные скрыты из ленты, строки в БД остаются.
  5. Контроллер пишет сообщение (status=pending) и ставит FanOutInAppNotificationJob в очередь default. Аудит: in_app_notification.created («Создание in-app уведомления»).

5) Кто видит сообщение

  1. Воркер резолвит пользователей: is_enabled=1, выбранные роли и школы, не роль superadmin. Пишет снимок в in_app_notification_recipients, статус dispatched.
  2. Кто заведён после отправки — старое сообщение не видит.
  3. Выключенный пользователь в снимок не попадает.
  4. Обычный пользователь видит уведомление, только если он в снимке.
  5. Superadmin в ленте видит сообщения текущей школы (session current_partner) плюс глобальные (is_global=1), даже если его не было в снимке. Чужую школу не видит, пока не переключит партнёра.
  6. Realtime: тот же Reverb, что у чата. Клиент Echo в includes/in_app_notifications/echo.blade.php (без wsPath: '/app'). Канал user.{id}, событие in-app-notification.bell. Кто офлайн — увидит каунтер из БД при следующем заходе. Оверлей процесса/сокета — при персональном флаге users.system_monitors и can(settings.systemMonitors.view) (анонс).

Форма для админа школы — позже (inAppNotifications.manage). Ручная рассылка по-прежнему только superadmin.

5.1) Автособытия

Первое автособытие: ученик (роль user) успешно добавил группу в ЛК (POST /cabinet/teams/attach, AJAX 200 и native POST 302). Колокольчик, не email. Анонсы: событие, текст тела.
  1. После транзакции attach CabinetTeamAttachedNotifier создаёт сообщение source = event через InAppNotificationDispatcher::dispatchEvent и ставит тот же FanOutInAppNotificationJob (очередь default). Пока job не выполнен, статус pending — в ленте и колокольчике пусто.
  2. Школа — partner_id ученика, которому повесили группу (семейный режим — активный ребёнок). Админы/тренеры другой школы не получают. Гость / 403 / 422 событие не создают.
  3. Роли: системные admin и trainer этой школы (is_enabled=1). Кастомные роли и ученики — нет. Выключенный сотрудник в снимок не попадает. Superadmin видит, когда выбрана эта школа. Кто заведён после fan-out — не видит.
  4. Тип normal (плашки нет), срок жизни 30 суток, created_by — автор действия в ЛК. Аудит ручной рассылки (in_app_notification.created) не пишется.
  5. Текст: без ссылки на карточку. Тело собирает CabinetTeamAttachedNotifier::buildBody (потом sanitizer: p / br разрешены).
    • Есть users.parent_id и непустое ФИО карточки parents (фамилия + имя + отчество, как колонка «Родитель») — три строки:
      Родитель: Иванов Иван
      Ребёнок: Комарова Ярослав.
      Добавлена группа «Штурм» (объект «Стадион «Исток»»). ФИО ребёнка — фамилия + имя ученика.
    • Нет родителя, soft-deleted карточка или пустое ФИО родителя — {ФИО} добавил группу «…» (объект «…»).
    • Семейный кабинет: родитель и ребёнок активного ученика; created_by — кто нажал.
    • Пустое ФИО ученика → Ученик #{id}; пустой объект → Объект #{id} или «объект не указан». Имена экранируются (e()).
  6. Сбой уведомления attach не откатывает: группа уже сохранена, ошибка в лог [CabinetTeamAttachedNotifier] failed.

Конфиг: config/in_app_notifications.php → events.cabinet_team_attached. Подробности attach — dashboard-cabinet §7.1.

6) Модель данных и конфиг

  1. in_app_notifications — тип (update / important / normal), source (manual / event), HTML-текст, is_global, audience_role_ids, expires_at, статус рассылки. action_url не заполняется.
  2. in_app_notification_partners — школы, если не глобальное.
  3. in_app_notification_recipients — снимок получателей в момент job.
  4. in_app_notification_reads — прочитанность в разрезе пользователя (и для superadmin).

config/in_app_notifications.php: dropdown_limit = 3, dropdown_preview_limit = 60, index_per_page = 20, events.cabinet_team_attached.
