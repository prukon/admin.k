Тренеры (админка)

Файл: /docs/documentation/admin-trainers.html · URL: /docs/documentation/admin-trainers · страница CRM: /admin/trainers · вкладки раздела: admin-users-section

1) Назначение и модель данных

Тренер — это обычная учётная запись users с системной ролью trainer и дополнительным профилем trainer_profiles (1:1 по user_id).
ФИО, email, телефон, пароль, аватар — в users; описание, флаг активности профиля и порядок сортировки — в trainer_profiles.
Отдельной таблицы «тренеры» с собственным ФИО нет (историческая trainers удалена миграцией рефакторинга).
Таблица / сущностьНазначение
roles.name = trainer Системная роль (сидер RolesSeeder, id=4). is_visible = 1 — отображается в матрице «Настройки → Права и роли» и как вкладка «Тренеры» в разделе «Пользователи» (при trainers.view). Базовые права — config/role_base_permissions.php → ключ trainer. Миграция 2026_06_16_120000_set_trainer_role_visible.php.
trainer_profiles Профиль тренера: partner_id, user_id (unique), trainer_type_id (FK на trainer_types, обязателен в приложении), description, is_enabled, sort_order, default_base_salary_cents, default_rate_per_training_cents (classic; HTTP — рубли, см. money), soft delete.
trainer_types Партнёрские типы тренера для схемы Канзас (имя, порядок, активность, оклад за тренировку, базовая премия). UI и CRUD только при kansas. Не входят в «Справочники». См. §6.3 и анонс на /doc.
team_trainer Связь группа ↔ тренер (many-to-many: у группы несколько тренеров; у тренера — несколько групп). Поля: partner_id, team_id, trainer_profile_id.

Миграции: 2026_05_20_140000_refactor_trainers_to_trainer_profiles.php, 2026_05_20_150000_create_team_trainer_table.php, 2026_08_15_140000_create_trainer_types_table.php.

Не путать: у ученика группы хранятся в pivot team_user (см. student-team-membership). Привязка тренера к группам — только через team_trainer; у тренера users.team_id при сохранении сбрасывается в null.

2) Доступ и маршруты

Маршруты /admin/trainers* в routes/web.php обёрнуты в middleware('can:trainers.view'). Без trainers.view страница тренеров и JSON карточки отвечают 403. Маршруты /admin/trainer-types* — вне этой группы: сотрудник ЗП без trainers.view может вести типы при Канзасе и schedule.trainerSalary.manage (см. §6.3). Отдельного пункта «Тренеры» в сайдбаре нет: вход в раздел — /admin/users («Пользователи»), вкладка «Тренеры» видна при trainers.view (см. admin-users-section).

3) Синхронизация профиля при смене роли

App\Services\TrainerProfileSyncService::syncForUser вызывается из UserService после обновления пользователя:

  • роль trainer → создать или восстановить (restore) trainer_profiles;
  • любая другая роль → soft delete существующего профиля по user_id.

Создание тренера через POST /admin/trainers сразу создаёт user с role_id = trainer и профиль. При обновлении через страницу тренеров, если у user была другая роль, но профиль остался — роль принудительно возвращается на trainer.

4) Привязка к группам

App\Services\TeamTrainerSyncService:

  • Из карточки тренера — массив team_ids[] в store/update: тренер привязывается к нескольким группам; лишние строки в team_trainer для этого профиля удаляются. Другие тренеры группы не снимаются. Привязка добавляет тренера в авто-чат группы; отвязка из чата не убирает (анонс).
  • Из группы — поле trainer_profile_ids[] в POST/PATCH /admin/team/{id} (TeamController, мультиселект): на группу назначается один или несколько тренеров; полный sync (пустой массив снимает всех).
  • Список групп — на /admin/teams при trainers.view колонка «Тренер» (trainer_label — ФИО через запятую в JSON /admin/teams/data, настройка в «Поля списка»). Без права колонка скрыта, но поле в JSON остаётся. См. Группы (админка).

UI: чекбоксы групп — resources/views/admin/trainers/_teams_checkboxes.blade.php; в модалках групп — мультиселект тренеров при @can('trainers.view').

5) Редактирование пользователя с ролью «Тренер»

В модалке editUser.blade.php при trainers.view и выбранной роли trainer: скрывается селект основной группы (team_id), показываются чекбоксы team_ids[]. UserService::update синхронизирует группы только если у актора есть trainers.view и в запросе передан ключ team_ids. JSON GET /admin/users/{user}/edit отдаёт trainer_team_ids для предзаполнения.

Подробнее о разделе пользователей: Пользователи в админке.

6) UI страницы /admin/trainers

  • Список: ФИО, email, телефон, колонки «Оклад по умолчанию» и «Ставка за тренировку» (поля профиля default_*, в Канзасе на карточке не редактируются), статус, действия. При Канзасе в тулбаре кнопка «Типы».
  • Создание — модалка без аватара; обязательны имя и фамилия; email и пароль опциональны (если не включён welcome — §6.2). Classic: поля default_base_salary, default_rate_per_training (рубли, numeric|min:0, можно с копейками → в БД *_cents). Канзас: обязателен селект trainer_type_id; поля classic скрыты и disabled; сохранение карточки default_* не затирает. Успех create/edit/delete карточки — toast (window.showToast: «Тренер успешно создан.» / «обновлён» / «удалён»), не showSuccessModal.
  • Редактирование — как у пользователя: аватар с cropper (editAvatar), маска телефона, смена пароля отдельной кнопкой (§6.4) → POST /admin/user/{id}/update-password (право users.password.update). Успех: поле очищается, всплывайка «Пароль успешно изменен» (#kidsMainToast / window.showToast), не showSuccessModal. Повтор того же пароля на клиенте не шлётся. Без права кнопка disabled (opacity-50 pe-none). Повторной отправки пароля по email на странице тренеров нет (только для учеников — admin-users §5.1.2). Анонс UX — toast, показ формы — /doc.
  • Ошибки валидации возвращаются JSON (422) и выводятся под полями формы.

6.1) Оклад и ставка по умолчанию (ЗП тренеров)

Схема classic: поля профиля default_base_salary_cents / default_rate_per_training_cents копируются в черновик при первом появлении тренера в месяце. Изменение в карточке не перезаписывает уже существующий черновик classic.

Схема kansas: оклад за тренировку и базовая премия берутся из типа тренера (trainer_types), не из полей профиля. Человек всегда равен своему типу; черновики Канзаса переписываются при смене сумм типа и при смене типа у человека. Слепки не пересчитываются. Сохранение карточки в Канзасе не затирает classic default_*. См. §6.3, ЗП §12 и анонс типов на /doc, анонс настроек месяца.

Права на расчёт ЗП — отдельные: схема schedule.trainerSalary.scheme.classic или schedule.trainerSalary.scheme.kansas (включает superadmin) плюс schedule.trainerSalary.view / manage (не trainers.view).

6.2) Welcome-письмо при создании (send_welcome_email)

Тот же механизм, что у учеников и сотрудников (admin-users §5.1.4).
  • UI: чекбокс «Отправить письмо» (#trainer-create-send-welcome-email), по умолчанию включён; при включении поле пароля скрывается.
  • При true: email обязателен; пароль генерируется на сервере; синхронная отправка ClientWelcomeCredentialsMail.
  • AJAX 200: message, trainer, welcome_email_sent. SMTP fail → пользователь/профиль созданы, welcome_email_sent: false.
  • Non-AJAX POST → redirect 302 на admin.trainers.index, запись создана.
  • Право: trainers.view (как у всего раздела).

6.3) Типы тренера (Канзас)

Партнёрский справочник шаблонов оплаты. UI только если у партнёра включена схема kansas (TrainerTypeAccess::partnerHasKansas = активная схема партнёра code === kansas; superadmin без выданной схемы → classic fallback → типов нет). Не входит в «Справочники». Анонс: /doc. Модалка стандартной ширины Bootstrap (modal-dialog, не на весь экран) на /admin/trainers (кнопка «Типы» при Канзасе) и на вкладке ЗП (кнопка «Типы тренеров» только при schedule.trainerSalary.manage).
ЧтоДетали
Таблицаtrainer_types: partner_id, name (unique per partner), sort_order, is_enabled, is_system, rate_per_training_cents, base_premium_cents
Системный типРовно один на партнёра, имя по умолчанию «Главный тренер» (можно переименовать). Нельзя удалить и отключить. Создаётся при создании партнёра и миграцией для существующих. Назначается всем тренерам.
Профильtrainer_profiles.trainer_type_id. При Канзасе селект обязателен. Classic поле скрыто, тип всё равно проставляется системный.
ПраваСписок/просмотр и назначение на карточке: trainers.view (или schedule.trainerSalary.view для GET списка). CRUD и суммы: schedule.trainerSalary.manage. Сотрудник ЗП без trainers.view может вести справочник. Без Канзаса endpoint’ы 403.
МаршрутыGET/POST /admin/trainer-types, GET/PUT/DELETE /admin/trainer-types/{trainerType} (admin.trainer-types.*). Чужой партнёр — 404.

Несистемный тип удаляется, только если на него никто не назначен (включая soft-deleted профили) — иначе 422 errors.name.

CRUD модалки (/admin/trainer-types) при успехе всегда JSON (message + trainer_type), в том числе без X-Requested-With — не пустой 200 и не redirect. UI: toast «Тип тренера сохранён» / «Тип тренера удалён» (window.showToast, не showSuccessModal). Удаление: кнопка #trainer-type-delete-btn → confirmDeleteType() → showConfirmDeleteModal('Удаление типа тренера', …) (не window.confirm). Текст: «Вы уверены, что хотите удалить тип тренера «Название»?». Модалка «Типы тренеров» остаётся открытой (очередь Bootstrap вернёт её после confirm; #trainerTypesModal не hide). Успех: AJAX DELETE → loadList('saved') → showList(), toast message сервера или «Тип тренера удалён». 422 — showAlert + errors.name в форме модалки типов. Ошибка валидации: AJAX → 422 errors[field]; non-AJAX → 302 и ошибки сессии под полями. Карточка тренера: non-AJAX create/update → 302 на /admin/trainers; AJAX → JSON 200/422.

6.4) «Изменить пароль» в модалке редактирования

Модалка #trainerEditModal, кнопка #trainer-change-password-btn («Изменить пароль»), форма #trainer-change-pass-wrap (классы buttons-wrap change-pass-wrap, поле #trainer-new-password, «Применить» / «Отмена»).
  • При первом открытии и после закрытия модалки блок скрыт (style="display: none").
  • В resources/css/style.css (Vite, layout admin2) у .change-pass-wrap стоит display: none. Поэтому клик не может ставить style.display = '' — CSS снова прячет форму, а кнопка уже скрыта. Нужен явный display: block.
  • «Отмена», hidden.bs.modal и успешное «Применить» вызывают resetTrainerPasswordUi: кнопка снова видна, блок display: none, поле пустое.
  • Сохранение пароля — тот же POST /admin/user/{id}/update-password, toast, skip повторного пароля: анонс, не success-модалка.
  • Не то же, что у ученика (jQuery $('#change-pass-wrap').show()), своего пароля в ЛК (display: inline-block) и сотрудника (#role-staff-change-pass-wrap без класса .change-pass-wrap). Resend пароля по email на этой странице нет.
Анонс: /doc §форма пароля тренера.

7) Тренеры в журнале /schedule (отметка «Посетил»)

При статусе «Посетил» можно указать одного или нескольких тренеров (мультиселект trainer_profile_ids[], KidsCrmGenericMultiselectSelect2). Пустой выбор = «Без тренера».
Источник истины для нагрузки и ЗП — pivot user_lesson_occurrence_status_event_trainers (каждому выбранному тренеру отдельный зачёт тренировки). Колонка user_lesson_occurrence_status_events.trainer_profile_id — legacy/primary (первый из списка).
UI: модалки ячейки и гибкого абонемента на /schedule; empty-cell — тот же мультиселект (дефолт = тренеры группы; BC trainer_profile_id). Право schedule.view (не trainers.view). По умолчанию при первом выборе «Посетил» — первый тренер группы из team_trainer; повторное открытие сохранённого «Без тренера» дефолт группы не подставляет.
Подробно: Журнал: тренеры при «Посетил», тесты ScheduleJournalMultiTrainerContractsFeatureTest. Агрегация — «Нагрузка тренеров» и «ЗП тренеров».

8) Фильтр «Тренер» в отчётах

Параметр: filter_trainer_profile_id (id из trainer_profiles). Логика: берутся team_id из team_trainer для выбранного профиля, затем отбираются ученики, состоящие хотя бы в одной из этих групп (pivot team_user). Если у тренера нет групп — отчёт пустой (whereRaw('1 = 0')).

Подробная таблица отчётов и отличие от фильтра локации: Отчёты: фильтр по тренеру.

  • Select2 поиск: GET /admin/reports/payments/trainers-search (reports.payments.trainers.search) — в группе reports.view; по ФИО user.
  • Отчёты: Платежи, Платежи по месяцам, LTV, Задолженности — тот же параметр в DataTables и …/total.
  • Фильтр «Активность ученика» (status, users.is_enabled) — в тех же отчётах и на «Назначение абонементов», без отдельного permission; см. reports-admin §2.3.

9) Изоляция по партнёру

  • Список и операции — только trainer_profiles.partner_id = current_partner.
  • Чужой профиль по id → 404 на show/update/destroy.
  • team_ids и trainer_profile_id валидируются: группа и профиль должны принадлежать текущему партнёру.
