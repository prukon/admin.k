Клиенты в админке (ученики)

Файл: /docs/documentation/admin-users.html · URL в CRM: /docs/documentation/admin-users · оглавление: /doc · вкладки раздела: admin-users-section
Вкладка «Клиенты» в разделе CRM «Пользователи» — это только ученики (roles.name = user, UI-label «Клиент»). Тренеры, администраторы и кастомные роли — на отдельных вкладках (обзор, тренеры, администраторы и кастомные роли). Анонс на /doc: нейминг «Клиенты», дозапись родителя при импорте Excel, создать договор со списка клиентов.

Нейминг: «Клиенты» vs «Пользователи»

Клиент в UI — ученик (роль user), не любой аккаунт CRM. Сайдбар и h4 раздела остаются «Пользователи». Toolbar h1 и вкладка на этой странице — «Клиенты», фильтр — «Все клиенты». Модалки: «Создание клиента» / «Редактирование клиента» / «Удаление клиента». JSON: Клиент создан успешно, Клиент успешно обновлён, Клиент успешно удалён (ё); toast удаления: «Клиент успешно удален.» (е). Не переименовывали: «пользовательские поля», импорт «учеников из Excel», тренеры, сотрудники («Пользователь создан»), право users.view («Страница "Пользователи"»), свой профиль в ЛК («Пользователь успешно обновлен»), отчёты «Все пользователи». Подробнее — admin-users-section §2–3, тесты — §автотесты ниже и /doc.

1) Назначение и доступ

Страница списка: GET /admin/users (маршрут admin.user1, UserController@index), view resources/views/admin/user.blade.php. Горизонтальные вкладки — admin/users/_users_section_tabs.blade.php.
Все маршруты раздела обёрнуты в middleware('can:users.view') (routes/web.php). Без users.view страница и AJAX раздела отвечают 403, даже если у роли есть locations.view или contracts.view.
Импорт из Excel — отдельное право users.import (§8): требует и users.view, и users.import. Сопоставление родителя по email — дозапись пустых ФИО/телефона, без требования полного совпадения (анонс, §8.4).
Колонка «Договор» в таблице и поле latest_contract в JSON — дополнительно только при contracts.view (§2.3); без него список пользователей доступен как раньше.
Внутренняя документация (/doc) требует отдельное право documentations.view — это не доступ к /admin/users.

2.0) «Показать N» — персонально на пользователя

Селект DataTables «Показать 10 / 20 / 50 / 100» на /admin/users сохраняется на текущего пользователя с правом users.view в user_table_settings.page_length для table_key = users_index (та же строка, что видимость колонок). Номер страницы (start) не хранится.

  • Старт. UserController::index читает page_length текущего пользователя и передаёт $usersPageLength в Blade. KidsCrmDataTable.create('#users-table') получает dataTable.pageLength и columnsSettings.persistPageLength: true. Нет записи / значение не из 10, 20, 50, 100 → 10.
  • Смена селекта. Пресет шлёт POST /admin/users/columns-settings только с page_length. Request: UserTableSettingsSaveRequest. Ключи sex / comment по-прежнему отфильтровываются без соответствующих прав (только когда в запросе есть columns). AJAX и non-AJAX успех → 200 {success: true} + запись в БД.
  • Ошибки. Невалидное значение: AJAX → 422 errors.page_length («Можно показать 10, 20, 50 или 100 записей.»), текст под .dataTables_length. Non-AJAX → 302 + session errors. Пустой POST по-прежнему 422/302 по columns.
  • GET columns-settings не отдаёт page_length — контракт видимости колонок не менялся. Сохранение колонок не сбрасывает page_length.

Тесты: UsersPageLengthFeatureTest (HTTP 200/403/422/302, UX: повторное открытие держит N, скрытие колонок не сбрасывает N, start не пишется), UsersPageLengthFullAccessFeatureTest (гость / без права / viewer / admin; PUT/PATCH/DELETE → 404/405), BladeInlineJsSyntaxTest::test_kids_datatable_page_length_persist_posts_only_page_length_not_page_number, BladeInlineJsSyntaxTest::test_only_opted_in_blades_enable_page_length_persist. Анонс — /doc. Тот же механизм на заявках — school-leads-widget §5.1.4.

2.1.2) UI и поиск (модалки create / edit)

Partial: resources/views/admin/users/_parent_form.blade.php (подключается в createUser / editUser; в заявках — с prefix=lead).

Видимость блока. Секция «Данные родителя» показывается только если в модалке выбрана роль user (ученик). При другой роли блок скрывается, поля parent_* отключаются и не уходят в сохранение. На сервере StudentParentSyncService для не-user сбрасывает users.parent_id в null.
Редактирование карточки из справочника (2026‑07). В режиме «Из справочника» видны и Select2, и поля ФИО/профиля (включая родительный падеж). Правка при сохранении с parent_id пишет в существующую строку parents — изменения общие для всех учеников с этим parent_id (список, edit JSON, семейный кабинет, договоры через parent_full_name / parent_full_name_genitive). Отдельного подтверждения при нескольких детях нет. Чтобы завести другую карточку — режим «Новый родитель» (очищает parent_id, создаёт новую запись). Подробнее о родительном — §2.1.6.

  • Если справочник пуст — переключатель и Select2 не рендерятся; сразу только поля ФИО нового родителя.
  • GET /admin/users/parents/search?q=... (и опционально id=) — JSON для Select2; только parents.partner_id = current. Если ФИО карточки пустое, подпись — Родитель #{id} (колонка списка при этом пустая, не этот fallback). Импорт Excel может дописать ФИО в пустые поля — тогда и Select2, и колонка показывают обычное ФИО (анонс).
  • Выбор из справочника подставляет ФИО и поля профиля в форму. Поля ФИО редактируемы. Режим «Новый родитель» очищает parent_id и показывает пустые поля — создаётся новая строка parents.

2.1.4) Валидация, сервис, логи

Trait ValidatesStudentParent в StoreRequest / UpdateRequest:

  • parent_id — nullable, exists в parents с partner_id = current.
  • parent_lastname, parent_firstname, parent_middlename — ключи HTTP-формы (не колонки users), nullable|string|max:100.
  • parent_full_name_genitive — ФИО в родительном падеже, nullable|string|max:300 → parents.full_name_genitive.

Сохранение: StudentParentSyncService::syncForStudent из UserService::update/store. При обновлении вызывается, если в теле есть ключи parent_* или у пользователя после сохранения роль не user (сброс parent_id).

Контракт HTTP: AJAX store/update → JSON 200 (message, у store ещё user); non-AJAX POST/PATCH без X-Requested-With → 302 на admin.user1 (safety-net). Валидация → 422 (AJAX) / redirect + session errors (web).

JSON edit: user.parent_lastname и т.д. — из User::parentFormFields() (значения из parents), в т.ч. user.parent_full_name_genitive.

8.4) Бизнес-логика

Ученик: create vs update

  • Create — пустой email ученика или email не найден у ученика текущего партнёра.
  • Update — email совпал с учеником (users.role_id = роль user, users.partner_id = current).
  • Email занят пользователем другой роли или другого партнёра → ошибка в preview (поле «Email ученика»).
  • Один email ученика в файле — одна строка; дубль в файле → ошибка.

Группы

  • Группа необязательна. Указана — поиск по teams.title (case-insensitive) в рамках партнёра.
  • Нет в справочнике → создаётся новая группа (нужно юр. лицо в строке); teams.legal_entity_id из найденного юр. лица.
  • Soft-deleted группа с таким названием → ошибка (восстановить вручную или сменить название).
  • Уникальность названия: индекс UNIQUE (partner_id, title) на teams (миграция 2026_07_04_100000_add_unique_partner_title_to_teams_table.php, с дедупликацией перед индексом).
  • При update с указанной группой — замена всех групп ученика на одну из строки (TeamUserSyncService::syncTeamsForStudent, одна группа на строку импорта).
  • При update с пустой группой — снятие всех групп.

Родители

  • Все поля родителя пустые при update → users.parent_id = null (отвязка). Карточка parents при этом не очищается.
  • parent_email пустой, но есть ФИО → новый родитель на каждую строку (запись в parents).
  • Одинаковый parent_email в нескольких строках → один родитель. Пустые ячейки ФИО/телефона между строками не конфликтуют (поля дополняют друг друга); ошибка только если одно и то же поле заполнено по-разному.
  • Родитель в справочнике (совпадение по email текущего партнёра, без учёта регистра): пустые ячейки ФИО/телефона не сравниваются и не очищают карточку. Непустое значение из файла дописывается в пустое поле parents (фамилия, имя, отчество, телефон). Если и в файле, и в карточке поле уже заполнено и значения различаются → ошибка «Родитель с таким email уже существует, но данные в файле не совпадают со справочником.» Заполненные поля справочника импорт не перезаписывает. Commit: UsersImportParentDirectory::fillEmptyFromRow, затем в sync уходит parent_id (чтобы StudentParentSyncService не затёр ФИО пустым payload). Чужой партнёр с тем же email не заполняется — создаётся своя карточка. После commit Select2/колонка «Родитель»/edit JSON показывают ФИО, а не «Родитель #id». Хелпер UsersImportParentDirectory. Анонс — /doc#users-import-parent-fill-index.
  • Контакты ученика (users.email, users.phone) и родителя (parents) — раздельно (как в §2.1); email родителя не копируется в email ученика автоматически.
  • Массовой чистки уже существующих безымянных карточек нет: без строки импорта они остаются как были.

Транзакция и аудит

  • Commit — одна DB::transaction на весь файл; при ошибке runtime после preview (например, гонка удаления ученика) — откат, 422.
  • Каждый create/update пишет аудит user.created / user.updated через AuditLogger (UsersImportCommitService).
  • Welcome-письмо при импорте не отправляется (в отличие от §5.1).
  • Доп. поля user_fields / мед.-флаги / пол / комментарий через импорт не задаются — только поля из шаблона.

8.5) Preview-diff перед commit (прозрачность update)

Цель — до нажатия «Импортировать» показать, что именно изменится у существующих учеников. Для ученика семантика commit не менялась: при update полная подстановка полей из строки Excel (пустые ячейки могут обнулить телефон/ДР, снять группы). Исключение — карточка родителя при совпадении email: пустые ФИО/телефон не очищают справочник, непустые дописываются в пустые поля (анонс, §8.4). Отвязка родителя по-прежнему, если в строке нет данных родителя вообще.

Когда считается

  • Только при успешном preview (valid: true) и только для строк с mode = update.
  • Строки create — changes: [], has_clears: false.
  • Diff не кладётся в cache токена: в users_import:{uuid} только строки для commit; diff строится заново на каждом preview.
  • Реализация: UsersImportPreviewDiffBuilder (+ DTO UsersImportFieldChange), вызывается из UsersImportValidator после валидации.

  • update_with_clears_count — update-строки, где есть хотя бы один kind: cleared.
  • Порядок в preview[]: сначала все строки с изменениями, затем остальные (create + update без изменений); внутри групп — порядок как в Excel.

  • Ширина модалки — обычный modal-dialog (без modal-lg: в проекте .modal-lg = 90% экрана).
Preview-diff — только прозрачность. Пустые ячейки ученика (телефон, ДР) и группы по-прежнему могут очистить данные при commit; оператор должен смотреть строки с пометкой «очистка» перед импортом. Пустая ячейка ФИО/телефона родителя при совпавшем email справочник не чистит. Отвязка родителя — только если в строке все поля родителя пустые.
