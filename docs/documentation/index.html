Назначения: фильтр «Прошедшие» и красная дата последнего занятия (2026‑08)

На вкладке «Назначение абонементов» (/admin/lesson-packages/assignments):

1) Чекбокс «Прошедшие» (filter_past_lessons=1): по умолчанию выключен — скрываются назначения, у которых дата последнего занятия (MAX(user_team_schedule_slots.starts_at)) строго раньше сегодняшней даты сервера. При включении прошедшие тоже показываются (вместе с остальными — include-фильтр). Назначения без слотов (ещё не раскиданы) всегда в списке. Сегодняшняя дата последнего занятия не считается прошедшей.
2) Колонка «Занятия»: строка «Посл.: …» красная (text-danger), если сервер отдал last_lesson_is_past=true (та же граница: строго до сегодня).

Подробно — lesson-packages §assignments-past-lessons, обзор вкладки — §assignments-tab.

Назначения: фильтр «Удаленные» ученики (2026‑08)

На вкладке «Назначение абонементов» (/admin/lesson-packages/assignments) чекбокс «Удаленные» (filter_deleted_users, value 1):
1) По умолчанию выключен — назначения soft-deleted учеников скрыты (whereNull(users.deleted_at)), даже если status=active / is_enabled=1.
2) При включении — include (как «Прошедшие»): в списке живые и удалённые; ФИО через withTrashed() (не «—»), бейдж «Удалён» (user_is_deleted в DataTables и модалке #ulp-modal-user-deleted-badge).
3) Модалка / update / lessons для назначения текущего партнёра не дают 404/403 из‑за soft-delete (withTrashed в контроллере и UpdateUserLessonPackageAssignmentRequest::authorize).
4) users-search удалённых не ищет; preselect filter_user_id — подпись «ФИО (удалён)».

Права те же: lessonPackages.view + setPrices.packageAssignments.view. Подробно — lesson-packages §assignments-deleted-users, фильтры — §assignments-tab. Тесты: LessonPackageAssignmentsDeletedUsersFilterFeatureTest.

Автопролонгация фиксированного абонемента (2026‑08)

На вкладке «Назначение абонементов» для классического fixed (не из «Установки цен» / без billing_month) — флаг «Автопролонгация» (создание и редактирование). На ученике одновременно не более одного ULP с включённым флагом.

1) Триггер: первое достижение lessons_remaining = 0 при списании статуса (календарь / журнал / автосписание) → FixedLessonPackageAutoProlongService после коммита транзакции.
2) Успех: новый ULP (та же цена, is_paid=false), раскладка по фактическим слотам текущего назначения, старт после последнего UTSS; флаг на новом; у старого — auto_prolonged_to_id; аудит user_lesson_package.auto_prolonged.
3) Ошибка: новый ULP не создаётся, флаг снимается, аудит user_lesson_package.auto_prolong_failed.
4) Жёсткий запрет: пока флаг активен — нельзя новые назначения / пробное / чужие привязки (assignments, календарь, журнал, sync из установки цен). Исключение — привязка самого автопролонг-ULP. Текст: UserLessonPackageAutoProlongGuard::BLOCK_REASON. В Select2 disable только при users-search?context=assign (создание назначения); календарь/фильтр ученика не блокируют выбор.

Подробно — lesson-packages §auto-prolong; календарь — school-schedule-calendar; sync цен — setting-prices-monthly-users §ulp-sync; аудит — audit-my-logs.

Календарь школы: шаблон фикса из слотов группы + превью цепочки (2026‑08)

На вкладке «Расписание школы» (/admin/lesson-packages/school-schedule, lessonPackages.view) при привязке фиксированного абонемента в модалке слота:

1) Автозаполнение «Шаблона привязки» — строки patterns[] сразу заполняются всеми активными слотами той же группы на том же объекте (fixed.group_patterns в GET …/slot-user-bind-actions): якорный слот первым, остальные по дню недели и времени (в т.ч. два слота в один день). Объект сравнивается точно (location_id, включая оба NULL). Активность sibling-слота — на ближайшую дату его дня недели (не на дату якоря), иначе ср/пт с поздним date_start отсекались. Строки можно править/удалять; «+ Добавить слот» — вручную.
2) Превью распределения под шаблоном (#schoolCalFixedChainPreview, выравнивание влево): «Распределение N занятий абонемента:» и список 6 августа 2026 17:00-18:00 (четверг). Если за период набирается меньше N — «найдено X из N». Данные — POST …/assign-fixed-preview (без записи в БД; debounce на фронте). Submit по-прежнему POST …/assign-fixed.

Документ: school-schedule-calendar § group_patterns, § превью; обзор в абонементах — lesson-packages § фиксированное расписание. Тесты: LessonPackageSchoolScheduleFixedGroupPatternsFeatureTest, LessonPackageSchoolScheduleFixedChainPreviewFeatureTest, SchoolSchedulePageFullAccessFeatureTest, BladeInlineJsSyntaxTest (fixed-bind + preview fetch).

Журнал: «Разложить абонемент» — группа → абонемент (2026‑08)

Журнал: занятия из гибкого абонемента «на лету» (2026‑08)

Месячный гибкий абонемент из «Установки цен» ставится в журнал /schedule по клику на ячейку (не цепочкой, как fixed).

Sync при установке цен (UsersPriceLessonPackageSync): для flexible сразу starts_at = 1-е число new_month, ends_at = последний день месяца. Hover при одном: «Остаток занятий в текущем месяце по абонементу "…" за Y руб» (цена 0 → «за 0 руб»). При остатке 0 — скрыто.

Ошибки Laravel под полями. После успешного AJAX без location.reload: обновляются ячейка дня (иконка/цвет статуса) и подпись N/M + Гибкий (renderScheduleCellAfterFlexiblePlace / updateFlexibleHintAfterPlace в schedule.js).
3) Занятая ячейка / ×N → кнопка «Добавить занятие из гибкого абонемента» (второе занятие в тот же день — другой служебный team_schedule_slot).
4) Фильтр группы → автовыбор; без фильтра и несколько групп — select. Только ULP с billing_month = месяц экрана (классика с вкладки «Назначения» — через календарь школы). Если есть гибкий с остатком, пустая ячейка открывает гибкий, а не постоплату.

AJAX → JSON 200 result: { utss_id, slots_remaining, lessons_total, status: { id, title, icon, color }, … } / 422 с errors; non-AJAX → 302, не пустой 200. Сервис JournalFlexibleAbonementPlacementService + UserLessonOccurrenceStatusService (списание при consumes_lesson).

Документы: schedule-journal §7.3, setting-prices-monthly-users § ULP sync, lesson-packages § billing_month, payments § billing_month. Календарь школы (inline assign-flexible) — school-schedule-calendar (оба пути пишут в один контур UTSS).

Право lessonPackages.type.postpay — тип «Постоплата» (2026‑08)

Скрытое право lessonPackages.type.postpay (группа lessonPackages, is_visible = 0) управляет выбором типа абонемента schedule_type = postpay. В базовые роли user / admin / trainer не входит; миграция только создаёт право, никому не выдаёт.

Карточка права — lesson-packages-type-postpay; бизнес-логика постоплаты — postpay.

Ручная смена даты окончания абонемента (2026‑07)

На вкладке «Назначение абонементов» (/admin/lesson-packages/assignments) в модалке «Изменение абонемента» можно править дату окончания назначения после того, как период уже задан первой привязкой к календарю школы.
1) starts_at по-прежнему только для просмотра; меняется только ends_at.
2) Пока период NULL (ещё не было привязки к календарю) — поле недоступно; в PUT поле ends_at prohibited.
3) Ограничения: ends_at ≥ starts_at и не раньше даты последнего занятия в календаре по этому назначению (max(user_team_schedule_slots.starts_at)).
4) При сохранении обновляется user_lesson_packages.ends_at и синхронизируется ends_at у связанных строк календаря; новые занятия не создаются и не удаляются (в т.ч. для фиксированного абонемента цепочка не достраивается).
5) Это не меняет правило конфликта assign-fixed: занятость ученика по-прежнему ключуется по user_team_schedule_slots.starts_at, а не по «хвосту» ends_at строки.

Конфликт привязки фиксированного абонемента: дата = starts_at (2026‑07)

При POST …/school-schedule/assign-fixed проверка пересечения времени у ученика смотрит только на дату занятия в календаре — user_team_schedule_slots.starts_at. Поле ends_at у строки календаря (для flexible/fixed/разового часто = конец периода назначения user_lesson_packages.ends_at; у пробного ends_at = starts_at) не разворачивает занятие на последующие дни недели.
Раньше интервал starts_at…ends_at + тот же weekday давал ложный «Конфликт расписания» на даты после последнего реального занятия, пока не истёк срок абонемента (например, новый фикс с якоря 27.07 при старой записи с starts_at=20.07 и ends_at=29.07).
Календарь недели, статусы и автосписание и раньше опирались на starts_at — проверка конфликта приведена к той же модели. Время в один и тот же день по-прежнему конфликтует; разные слоты без пересечения часов в один день — нет.
Проверка кросс-слотового пересечения времени есть только у assign-fixed (цепочка). Гибкий / разовое / пробное проверяют дубликат «тот же слот + дата» (starts_at), без сравнения часов между разными слотами.
Подробно — school-schedule-calendar § конфликт, lesson-packages § фиксированное / конфликт.

В «Исходящих письмах» добавлена колонка «Партнер» и endpoint …/emails/partners-search. Единое описание — reports-admin §2.4.

Изменения в справочниках (юр. лица и группы, 2026‑06)

Юр. лица (/admin/legal-entities): публичное наименование в списке и привязках — PartnerLegalEntity::displayTitle() (organization_name → fallback title); поле «Наименование организации» обязательно в модалках CRM; колонка «Регистрация в банке» — бейдж + иконка i с KidsCrmTooltip; ошибка удаления при привязанных группах — модалка showErrorModal (не alert); после удаления модалка редактирования не открывается повторно. Подробно — admin-legal-entities.

Группы (/admin/teams): при ≥2 активных юр. лицах поле «Юр. лицо» в модалках обязательно; без привязки группы T‑Bank недоступен (жёсткий guard). Колонка «Юр. лицо» — displayTitle() явной привязки; без привязки — «—». Подробно — admin-teams §5.2, payments §2.3.5.

Общее: несколько юр. лиц на партнёра; CRUD в модалках; sm-register на карточке /admin/legal-entities/{id} (legal_entities.sm_register); LegalEntityResolver для оплат — ShopCode и реквизиты только из partner_legal_entities (без fallback на partners). При одном активном юр. лице группа может быть без legal_entity_id — резолвер использует единственное юр. лицо.

Организация партнёра (2026‑06‑30): реквизиты и НДС — только в «Юр. лица»; с карточки партнёра и вкладки «Организация» в ЛК убраны legacy-поля, а также город, индекс и данные руководителя (поле title переименовано в UI в «Название школы/секции»). Legacy-колонки partners.* в БД сохранены, приложение их не пишет из форм (PartnerLegacyLegalFields). Подробно — account-partner-organization.

Изменения в оплатах (T‑Bank, 2026‑06)

Глобальный терминал T‑Bank: ключи eacq/e2c — одна запись payment_systems(partner_id=NULL) на /admin/settings/paymentSystem. Автовыплата и задержка — в правилах комиссий (tbank §5), не в платёжных системах и не в глобальной задержке settings. Per-partner payment_systems(tbank) устарели.

Юр. лицо в админке T‑Bank (снимок legal_entity_id): колонка «Организация» в списке выплат (tbank-admin-payouts §4.1); строка «Организация» и timeline из 4 шагов на карточке платежа (tbank §5.7). Колонка «Партнёр» — по-прежнему название клуба (partners.title), не юр. лицо.

Группа платежа (team_id): для всех типов оплат (месячный взнос, клубный, доп. платёж, абонемент) юр. лицо и выплата определяются через группу в payables.meta.team_id — PayableTeamResolver (payments §2.3). В админке: колонка «Группа» в доп. платежах; для назначений абонементов группа задаётся при создании (multi legal entity) и в модалке занятий — lesson-packages §assignments-tab; backfill — миграции 2026_06_29_150000 + 2026_06_29_160000.

CloudKassir (чеки): ИНН принципала, наименование и НДС — из юр. лица по той же цепочке (forFiscalReceipt → payable → группа). Без meta.team_id и привязки группы к юр. лицу чек не собирается. СНО — из env платформы; partners.email, phone, website — по-прежнему с партнёра. Подробно — admin-legal-entities §5.1.

Feature-тесты оплат/T‑Bank/чеков: в фикстурах нельзя полагаться на legacy partners.tinkoff_partner_id / tax_id — только справочник юр. лиц + цепочка через группу. Хелперы CrmTestCase — tests-standards §5.

Multi-entity guard (2026‑06‑30): при ≥2 активных юр. лицах Init T‑Bank запрещён, если у выбранной группы нет активной привязки teams.legal_entity_id с ShopCode; ошибка Init — «Для выбранной группы не настроено юр. лицо». Клубный взнос: кнопки T‑Bank скрываются JS до выбора группы с доступным ShopCode. Подробно — payments §2.3.5, admin-legal-entities §1.1.

«Поставщик услуг» на витрине (2026‑07): на POST /payment, /payment/club-fee и публичной странице оплаты абонемента GET /pay/ulp/{token} (при T‑Bank СБП) показывается строка с юр. лицом, которому уйдёт net-выплата и которое попадёт в чек CloudKassir — та же цепочка, что при Init (PayableTeamResolver → LegalEntityResolver). Формат: {organization_name}, ИНН {tax_id}, {city}. На витрине ученика без валидного юр. лица — «Обратитесь в школу», кнопки T‑Bank скрыты; на публичной ссылке — «Обратитесь в школу/клуб.» Робокасса на витрине не затрагивается. Подробно — payments §3.1.2, публичная СБП-страница — payments §3.4.1.
